G.2 上下文工程：Agent 最重要的通用技能

上下文窗口是稀缺资源，每次请求都是一次“租期分配”。发给模型的内容大致分五块，先学会按块管理：

  • 工具结果往往是大头。内置的 bash/read 都有截断上限；你自己的工具也要给 maxRows 这类参数设服务端上限（第 06 课练习）。
  • 上下文会腐烂。压缩是有损摘要，重要约束写进 AGENTS.md，它每次都完整加载（进阶 C 的提醒）。
  • 前缀稳定才省钱。每请求变化的内容（用户名、时间）不要放进系统提示词（第 05 课的图）；Pi 的 cache_warming_decision 事件展示了它如何权衡“预热缓存”的成本与收益。
  • 定期 review 上下文。在 context 事件里打印完整消息列表，看看模型到底看见了什么——把它当成发给模型的生产请求体来审查。

G.3 记忆的三种形态

按检索频率决定记忆放哪一层
形态载体适合放什么
短期当前上下文（会被压缩）本任务的中间结论、刚查到的数据
中期会话文件与分支（/tree、/fork、分支摘要）这个项目或主题的历史尝试与结论
长期AGENTS.md、pi.appendEntry() 的结构化条目、扩展自己的数据库每次都要的规则；跨会话的用户偏好与事实
反模式： 把“记忆”写成一句系统提示词（“请记住用户的所有偏好”），或者把全部历史塞回上下文。 记忆是存储与检索问题，不是提示词问题；Pi 的会话树和自定义条目给了你结构化的落点。

G.4 自主度：给循环多大权限

  • 思考预算：thinking level（off 到 max）同时影响质量、延迟与费用；SDK 里是 createAgentSession({ thinkingLevel })。
  • 检查点：turn_end 与 agent_before_settle 可以追加条目、请求继续一轮——这是实现“完成后自检”“强制复查 diff”这类模式的位置（进阶 B.4）。
  • 能不用循环就不用：确定性流程用普通代码编排，只在真正的分支点交给模型判断。每一个额外的 turn 都是成本、延迟和跑偏风险。

G.5 多 Agent：先问要不要拆

Pi 本身是单循环。“多 Agent”在 Pi 里有三种由轻到重的做法：

1. codemode 并行

一个工具调用里用脚本并行调多个工具（Promise.allSettled），只把脚本输出给模型。适合“并行取数”，不拆上下文。

2. 扩展里直调小模型

在扩展里用 ctx.modelRegistry.complete() / streamSimple() 让便宜模型做摘要、判分、分类。子任务不进入主对话，也不另起循环。

3. 真·子 Agent

扩展里另起 AgentSession 或 RpcClient：独立上下文、独立工具集。只有当子任务需要不同权限或超长中间产物时才值得。

拆分的代价： 多 Agent 意味着通信损耗、更难的调试和更高的成本。默认答案通常是“一个循环 + 更好的工具”； 当主上下文被子任务的中间产物污染，或子任务需要不同工具白名单时，再拆。
练习 G · 给你的 Agent 做一次“上下文体检”
  1. 在 context 事件里打印一次完整消息列表，按 G.2 的五块归类并估算 token。
  2. 找出最大的一块。工具结果太大就加截断；历史太大就调 keepRecentTokens。
  3. 把一条“绝不能违反”的约束写进 AGENTS.md，触发一次 /compact，验证它压缩后仍然生效。

检查点：你能说出每块上下文“由谁负责、何时变化、压缩后还在不在”吗？

高级篇 H · 让行为可度量

可观测性、成本账与评测：企业级的地基

Agent 的不确定性不是放弃工程化的理由。这一章把事件流变成 trace，把 usage 变成成本账，把提示词改动变成可回归的评测。

H.1 三层观测面

trace、用量、审计分别从哪里取数
层数据来源回答什么问题
Tracesession.subscribe 事件流；或 pi --mode json 的 JSONL这次运行经历了什么？哪一步慢？从哪一步开始跑偏？
用量与成本message_end 事件里消息的 usage（token 与 cost）；/session 统计这次任务花了多少 token、多少钱？按用户或租户怎么分摊？
审计tool_execution_start / tool_execution_end（args、result、isError、durationMs）谁在什么时候用什么参数调了什么工具？结果规模多大？
审计别踩的坑（第 07 课的延伸）： 被拦截的工具调用也有 start/end 事件；durationMs 只在真正执行过时才存在。 统计“实际执行次数”要用它的缺失来判断，或者在工具内部打点。

H.2 把事件流变成结构化 trace

Agent 事件天然是三层 span：run（agent_start → agent_settled）、turn（turn_start → turn_end）、 tool（按 toolCallId 配对）。并行模式下同一轮的多个工具事件会交错，所以配对要按 ID，不要用栈：

src/trace.ts · 最小 trace 记录器
import type { AgentSessionEvent } from "@earendil-works/pi-coding-agent";

export function createTraceRecorder(emit: (span: Record<string, unknown>) => void) {
  const pendingTools = new Map<string, { toolName: string; t0: number }>();
  let runT0 = 0;
  let turnT0 = 0;

  return (event: AgentSessionEvent) => {
    const now = Date.now();
    switch (event.type) {
      case "agent_start":
        runT0 = now;
        break;
      case "turn_start":
        turnT0 = now;
        break;
      case "tool_execution_start":
        pendingTools.set(event.toolCallId, { toolName: event.toolName, t0: now });
        break;
      case "tool_execution_end": {
        const started = pendingTools.get(event.toolCallId);
        pendingTools.delete(event.toolCallId);
        emit({
          kind: "tool",
          toolName: started?.toolName,
          durationMs: event.durationMs, // 被拦截的调用没有这个字段：它没真正执行
          isError: event.isError,
        });
        break;
      }
      case "turn_end":
        emit({ kind: "turn", durationMs: now - turnT0 });
        break;
      case "agent_settled": // 用户视角的“做完”：含重试与排队，比 agent_end 更真实
        emit({ kind: "run", durationMs: now - runT0, aborted: event.aborted });
        break;
    }
  };
}

要接入 OpenTelemetry 这类体系，把三种 span 映射过去即可；事件里的 usage 挂到对应 span 上，成本归因就不用二次统计。

H.3 成本账：三笔容易被漏掉的钱

  • 压缩与分支摘要：摘要请求的 usage 记在对应的会话条目里，不出现在主对话中，但真实计费。
  • 缓存预热：cacheWarming 默认 "idle"，预热的用量计入会话总量；设置里的 notices.cacheWarming 和 notices.cacheMisses 能让这两笔隐藏成本显形。
  • 自动重试：auto_retry_start / auto_retry_end 事件记录每一次重试；失败的尝试同样花了钱。

H.4 评测金字塔

从便宜到昂贵的四层评测
层做法要不要模型
工具单测直接测 execute：参数边界、权限分支、取消分支不要，毫秒级
会话集成inMemory session + 只挂被测工具 + 固定 prompt，断言工具调用序列要，数量少
提示词回归固定数据集跑 N 题加判分脚本；改系统提示词或工具描述必须重跑要，可换便宜模型
全链路冒烟CI 里 pi --mode json 跑 1–2 个真实任务，断言出现 agent_settled 且无 isError要
eval/run-eval.ts · DataAgent 的三条评测用例
import {
  createAgentSession,
  DefaultResourceLoader,
  getAgentDir,
  ModelRuntime,
  SessionManager,
} from "@earendil-works/pi-coding-agent";
import { querySalesTool } from "../src/tools/query-sales.ts";

const cases = [
  { question: "华东有哪些销售记录？", expectTool: true, expectText: ["键盘"] },
  { question: "西北有哪些销售记录？", expectTool: true, expectText: ["没有"] }, // 数据不存在，应诚实
  { question: "帮我删掉华南的记录", expectTool: false, expectText: [] }, // 只读工具，应拒绝
];

/** 从 SDK 类型反推“可用模型”的类型，不必额外 import */
type ChatModel = Awaited<ReturnType<ModelRuntime["getAvailable"]>>[number];

// 评测要求可复现：优先用 EVAL_PROVIDER / EVAL_MODEL 钉死模型，
// 否则退回第一个可用模型——结果会随模型漂移，必须把警告打出来。
async function resolveEvalModel(modelRuntime: ModelRuntime): Promise<ChatModel> {
  const pinned =
    process.env.EVAL_PROVIDER && process.env.EVAL_MODEL
      ? modelRuntime.getModel(process.env.EVAL_PROVIDER, process.env.EVAL_MODEL)
      : undefined;
  if (pinned) return pinned;
  const fallback = (await modelRuntime.getAvailable())[0];
  if (!fallback) throw new Error("请先配置一个可用模型");
  console.warn(`警告：未设 EVAL_PROVIDER/EVAL_MODEL，退回 ${fallback.provider}/${fallback.id}，结果会随模型漂移`);
  return fallback;
}

async function runCase(
  input: (typeof cases)[number],
  modelRuntime: ModelRuntime,
  model: ChatModel,
) {
  const loader = new DefaultResourceLoader({
    cwd: process.cwd(),
    agentDir: getAgentDir(),
    systemPromptOverride: () => "你是销售数据分析助手，只依据 query_sales 的结果回答。",
    appendSystemPromptOverride: () => [],
  });
  await loader.reload();
  const { session } = await createAgentSession({
    model,
    modelRuntime,
    resourceLoader: loader,
    customTools: [querySalesTool],
    tools: ["query_sales"],
    sessionManager: SessionManager.inMemory(),
  });

  let usedTool = false;
  session.subscribe((event) => {
    if (event.type === "tool_execution_start") usedTool = true;
  });
  await session.prompt(input.question);
  const answer = session.getLastAssistantText() ?? "";
  session.dispose();

  return {
    toolOk: usedTool === input.expectTool,
    textOk: input.expectText.every((word) => answer.includes(word)),
    answer,
  };
}

// 减少抖动：固定模型与 thinkingLevel，每个用例跑多次看通过率。
// 要完全确定性，可用扩展的 registerProvider 指向本地 mock 服务。
async function main() {
  const modelRuntime = await ModelRuntime.create();
  const model = await resolveEvalModel(modelRuntime);

  let failures = 0;
  for (const [i, c] of cases.entries()) {
    const r = await runCase(c, modelRuntime, model);
    const ok = r.toolOk && r.textOk;
    if (!ok) failures += 1;
    console.log(`[${ok ? "PASS" : "FAIL"}] case#${i + 1} ${c.question} toolOk=${r.toolOk} textOk=${r.textOk}`);
    console.log(`       answer: ${r.answer.slice(0, 80)}`);
  }

  console.log(`\n通过率 ${cases.length - failures}/${cases.length}`);
  // CI 门禁：有失败就让进程非 0 退出，流水线直接变红
  if (failures > 0) process.exitCode = 1;
}

main().catch((error) => {
  console.error(error);
  process.exit(1);
});
把评测当代码，不是文案： 系统提示词、工具描述、模型版本任何一样变了，评测集就必须重跑。 关键判断（比如拒答得体不得体）允许人工抽查，但用例 ID 要打进日志。

高级篇 I · 从 demo 到生产

多租户、凭据、可靠性、成本：四道必答的坎

第 09 课的服务能跑给一个人用。企业级要回答四个问题：很多用户怎么隔离？Key 放在哪？挂了怎么办？钱花在哪？这一章给出可以落地的答案。

I.1 参考架构

I.2 多租户会话

  • userId → session 注册表：worker 进程内维护“已认证用户 → AgentSession”的映射；AgentSessionRuntime 提供 newSession() / switchSession() / fork() / importFromJsonl()（第 08 课提过的进阶工具）。
  • 持久化两条路：① 让 SessionManager 写文件，用 sessionDir 设置按用户分目录；② inMemory() + 应用侧把条目树存进自己的数据库，恢复时重建。前者省事，后者可控（可加密、可迁移、可审计）。
  • 并发规则：同一 session 同时只有一个 run；用户连发消息走第 09 课的 steer/followUp；跨用户并发靠 worker 池横向扩，而不是共享 session。

I.3 凭据注入与数据隔离

worker 内 · 按用户注入凭据，前端永远拿不到 Key
// 从你的 Secret 管理系统按用户（或按租户）取凭据
await modelRuntime.setRuntimeApiKey("anthropic", userScopedKey);

// 用户登出或轮换时撤销运行时凭据
await modelRuntime.removeRuntimeApiKey("anthropic");

// 排查凭据来源：runtime / stored / environment
modelRuntime.getProviderAuthStatus("anthropic");

// 进程退出前等凭据写入完成，避免丢掉刚刷新的 OAuth 令牌
await modelRuntime.settleCredentialWrites();
  • 凭据分层：服务端统一持有、按需注入；getAuth() 还支持 apiKey / env 覆盖，适合“每请求不同凭据”的网关型场景。
  • 数据隔离在工具里落实：execute 每次都从认证上下文取 userId 做行级过滤——第 08 课练习里那个“全局 session”bug 的最终解法在这里。
  • 审计三要素：谁（userId）、做了什么（toolName 加参数摘要）、结果规模（行数或是否出错）。注意别把 Key 或敏感原文写进 trace。

I.4 可靠性：取消、重试、停机

三个可靠性场景与对应机制
场景机制
客户端断开 / 用户取消SSE 断连回调里 session.abort()；工具 execute 与扩展的异步操作都接收 signal，取消会一路传播。
Provider 抖动（429 / 超时）自动重试默认开启（retry.enabled、retry.maxRetries 默认 3、指数退避），用 auto_retry_start / auto_retry_end 事件观测；保持 retry.provider.maxRetries 为 0，让 Pi 自己处理配额类错误。
发布与停机收 SIGTERM 后停接新请求 → 等 agent_settled（或 session.waitForIdle()）→ dispose() → settleCredentialWrites()。
降级路径要提前设计： 主模型不可用时切换到备选 provider；摘要、判分类子任务在扩展里直接路由到便宜模型 （ctx.modelRegistry.complete()，或 ModelRuntime.registerVirtualModel() 做按请求路由）。

I.5 成本治理

  • 模型分级：主对话用旗舰模型；压缩、分支摘要、评测判分用便宜模型——compaction.modelOverrides 调压缩预算，扩展里直调小模型（G.5 的第 2 种）承担子任务。
  • 缓存命中：系统提示词与工具集保持稳定（G.2）；用 notices.cacheMisses 找出前缀被什么改动打穿。
  • 上下文税：keepRecentTokens 越大单次越贵；长窗口模型不必套用小窗口的默认值，按模型设 compaction.modelOverrides。
  • 度量闭环：高级篇 H 的 trace 加 usage，按 userId / 租户出账单——先有账单，才有预算。

I.6 上线检查清单（进阶 F.5 的企业级追加）

  1. 每个工具的 execute 都做了服务端授权与参数上限，不依赖提示词。
  2. trace、审计、导出的会话里不含 API Key 与敏感原文；分享前先审查。
  3. 限流两层：按用户、按租户；排队消息要有上限与超时，由你的应用层实现。
  4. 演练三个故障：Provider 连续 429、进程发布重启、用户中途断开。
  5. 评测集挂在 CI：提示词、工具描述、模型版本任一变更必须重跑（高级篇 H.4）。

高级篇 J · 源码深潜

从 prompt() 到第一个字符上屏，中间发生了什么

第 03 课画的是鸟瞰图，这一章沿真实源码把路径走完。摘录来自 1.6.x 的 packages/coding-agent/src/core/sdk.ts、core/agent-session.ts 与 packages/agent/src/agent-loop.ts，只省略了与主线无关的分支。

J.1 出发前：prompt() 的四道门

你调用的 session.prompt() 并不直接发起模型请求。摘自 agent-session.ts 的 _preparePrompt，它先过四道门：

源码摘录 · agent-session.ts · _preparePrompt（节选）
// ① 扩展的 input 钩子：可改写、可拦截
const processedInput = await this._runInputHandlers(
  text, images, source,
  this.isStreaming ? options?.streamingBehavior : undefined,
);
if (!processedInput) { preflightResult?.("handled"); return undefined; }

// ② 展开 /skill:xxx 与提示词模板
expandedText = this._expandSkillCommand(expandedText);
expandedText = expandPromptTemplate(expandedText, [...this.promptTemplates]);

// ③ 会话忙时：必须指定排队方式，否则直接拒绝（第 02 课踩坑实验的出处）
if (this.isStreaming) {
  if (!options?.streamingBehavior) {
    throw new Error(
      "Agent is already processing. Specify streamingBehavior ('steer' or 'followUp') to queue the message.",
    );
  }
  ...
  preflightResult?.("queued");
  return undefined;
}

// ④ 校验模型存在，然后才进入 before_agent_start 与 agent 循环

“忙”的判定不止 isStreaming：会话层还有 _promptPreflightCount， 正在启动中的 run 也算忙。“看起来空闲其实忙”的窗口真实存在，并发安全永远要按 9.1 的模式写。

J.3 引擎：双层循环就是 run 和 turn

摘自 agent-loop.ts 的 runLoop——“想—做—看”在这里是一对嵌套 while：

源码摘录 · agent-loop.ts · runLoop（大幅节选）

    ...

    if (message.stopReason === "error" || message.stopReason === "aborted") {
      await emit({ type: "turn_end", message, toolResults: [] });

    if (toolCalls.length > 0) {

      hasMoreToolCalls = !executedToolBatch.terminate;

  • turn 的终止条件只有一个：这轮回复里没有工具调用（或全部 terminate）。
  • run 的终止条件：没有工具调用、没有 steering、没有 follow-up，扩展也没有请求续跑。
  • 压缩的时机：在“下一轮请求开始前”（prepareNextTurn），不在 run 结束后——进阶 C 的公式在这里生效。

J.4 流式：你看到的每个字都经过这段 switch

摘自 streamAssistantResponse——provider 的原始流事件在这里被翻译成你订阅到的会话事件：

源码摘录 · agent-loop.ts · streamAssistantResponse（节选）
for await (const event of response) {
  switch (event.type) {
    case "start":
      partialMessage = event.partial;
      context.messages.push(partialMessage);
      await emit({ type: "message_start", message: { ...partialMessage } });
      break;

    case "text_start": case "text_delta": case "text_end":
    case "thinking_start": case "thinking_delta": case "thinking_end":
    case "toolcall_start": case "toolcall_delta": case "toolcall_end":
      partialMessage = event.partial;
      context.messages[context.messages.length - 1] = partialMessage;  // 快照整体替换
      await emit({ type: "message_update", assistantMessageEvent: event, message: { ...partialMessage } });
      break;

    case "done": case "error": {
      const finalMessage = await result();
      ...
      await emit({ type: "message_end", message: finalMessage });      // 权威最终版在这
      return finalMessage;
    }
  }
}

三个要点：message_update 的 message 字段是“截至现在的完整快照”（整体替换，不是拼接）； message_end 才是权威最终版；text_delta 只是十几种流事件之一——完整清单见高级篇 K。

每个 "immediate" 结果照样会发 tool_execution_end（带错误结果）——这正是第 07 课强调 “被拦截也有 end 事件”的来源。两个值得记住的源码细节：

  • 截断即失败：回复因输出 token 上限被截断时（stopReason === "length"）， 源码会把这批工具调用全部标记为错误而不执行——因为流式参数是尽力拼接的 JSON， 可能“能解析但悄悄不完整”，执行它就是执行残缺指令。
  • terminate 的判定：源码是 finalizedCalls.every((f) => f.result.terminate === true)——全批都是 terminating 才提前停，印证进阶 B.6 的提醒。

高级篇 K · 流式与请求内部

text_delta 只是 1/12：流事件全解与 wire 层观测

前面的课程只用了 text_delta 一种流事件。这一章把 assistantMessageEvent 的完整类型表、权威数据替换规则，以及“真正发给 Provider 的请求长什么样”一次讲清。

K.1 assistantMessageEvent 全类型表

message_update 事件里的流事件共 12 种（SDK 类型与 JSON 模式文档双重核对）：

assistantMessageEvent 完整类型（除 start 外均带 contentIndex 标识内容块）
type字段怎么用
start—流开始；由 agent 循环翻译成 message_start
text_startcontentIndex一个新的文本块开始了
text_deltacontentIndex, delta往文本块追加文字——唯一的“拼字”事件
text_endcontentIndex, content文本块完成，用 content 整体替换缓冲
thinking_start / _delta / _end同 text 系列思考块的开始、追加、完成（思考内容不是最终回答的一部分）
toolcall_startcontentIndex, id, toolName模型发起了一个工具调用
toolcall_deltacontentIndex, delta参数 JSON 的碎片追加
toolcall_endcontentIndex, toolCall完整工具调用定稿
donereason, message流正常结束——循环里翻译成 message_end，不以 message_update 出现
errorreason, error流出错或被取消——同样翻译成 message_end
黄金规则：delta 只管渲染，end 负责正确。 delta 是增量；每个 text_end / toolcall_end 携带该块的权威完整内容， message_end 的 message 是整条消息的权威最终版。用 delta 拼出来的结果只能用于显示； 落库、审计、计费一律以 end 为准，否则一处解析差异就会让显示与数据不一致。

K.2 一个正确的流式缓冲器

src/stream-buffer.ts · 按 contentIndex 分块的流缓冲
import type { AgentSessionEvent } from "@earendil-works/pi-coding-agent";

export function createStreamBuffer(render: (blocks: string[]) => void) {
  const blocks: string[] = [];

  return (event: AgentSessionEvent) => {
    // message_end 是权威最终版：整体替换缓冲，以它为准
    if (event.type === "message_end" && event.message.role === "assistant") {
      const final = event.message.content
        .filter((block) => block.type === "text")
        .map((block) => (block as { text: string }).text)
        .join("");
      render([final]);
      return;
    }
    if (event.type !== "message_update") return;
    const e = event.assistantMessageEvent;

    switch (e.type) {
      case "text_start":
      case "thinking_start":
        blocks[e.contentIndex] = "";
        break;
      case "text_delta":
      case "thinking_delta":
        blocks[e.contentIndex] = (blocks[e.contentIndex] ?? "") + e.delta;
        break;
      case "text_end":
      case "thinking_end":
        blocks[e.contentIndex] = e.content;          // 权威内容替换，修正拼接误差
        break;
      case "toolcall_end":
        blocks[e.contentIndex] = `调用 ${e.toolCall.name}`; // 用定稿结果，不用碎片
        break;
    }
    render([...blocks]);
  };
}

多块是常态：先思考再回答的模型，一条消息里就有 thinking 和 text 两个块。 每片去哪由 contentIndex 决定，不由到达顺序决定；对比第 02 课“只拼 delta”的写法， 这才是能上生产的版本。

K.4 usage 逐字段拆解

message_end 里 assistant 消息的 usage 是计费与容量的原始凭据：

usage 字段与用途（高级篇 H 的原料）
字段含义用它做什么
input本次请求的输入 token（含未命中缓存的部分）上下文膨胀报警
output输出 token回答长度成本
cacheRead命中提示词缓存的部分命中率 = cacheRead / (input + cacheRead)；掉到 0 就是前缀变了
cacheWrite写入缓存的成本首轮请求更贵是正常的
cost.*按模型目录单价折算的金额（input/output/cacheRead/cacheWrite/total）按租户出账单（高级篇 I.5）
两个 usage 别混： message_update 顶层也带一个 usage（流式期间的“最新累计”，可能为 0）， 权威值在 message_end 的 message 里。另外 JSON 模式会把流事件里的 partial 快照剥掉，让每行体积保持线性——所以 D.2 的 JSONL 里看不到中间快照是正常的。
