进阶篇 A · 日常使用

在终端里用 Pi：不写代码也能干活

前面的课程是从 SDK 写代码。但 Pi 首先是一个能在终端里读写你本地文件的助手。这一节讲你每天会碰到的界面、命令和选项，以及它们各自的边界。

A.1 安装与启动

终端：安装并确认版本
npm install -g --ignore-scripts @earendil-works/pi-coding-agent
pi --version
cd /path/to/your/folder
pi

需要 Node.js 22.19 或更新版本。先 cd 到你要工作的目录再启动：Pi 用这个目录查找文件、读取项目配置，也用它给会话分组。

A.2 第一次使用：登录、选模型

启动后最常用的几个斜杠命令
命令作用
/login选择 provider，用订阅或 API Key 登录。
/model切换可用模型；按 Ctrl+L 也能打开同一个选择器。
/thinking设置推理强度；按 Shift+Tab 循环切换。
/settings修改常用偏好。
/hotkeys查看当前生效的快捷键。

A.3 给任务：用 @ 引用文件

在编辑框里输入 @ 可以搜索文件并加入提示词，Tab 补全路径。Pi 读文件、搜索、执行命令、编辑文件时都会把过程显示出来，但不会每一步都请求你确认。

可以直接在 Pi 里输入的任务示例
Summarize @meeting-notes.md and save the action items to action-items.md.
Compare @previous.csv with @current.csv and summarize the important changes.

A.4 中途插话：排队、追加、停止

Pi 正在工作时，你可以继续输入
你想做的事操作
调整当前任务输入后按 Enter：等当前回复和工具调用结束后，指导下一步。
在当前任务之后追加一件事按 Alt+Enter：等整个任务结束后再处理。
把排队的消息拿回编辑框按 Alt+Up。
停止当前任务按 Escape，排队消息会回到编辑框。

Windows Terminal 会占用部分 Alt 组合键，遇到问题见 terminal-setup.md 的替代方案。

A.5 在脚本里用 Pi：--print 与 JSON 模式

终端：非交互用法
pi --print "Summarize this repository"
git diff | pi --print "Review this change"
pi --mode json "Inspect this repository" > events.jsonl
三种输出方式的区别
选项输出适合
--print / -p运行提示词，把最终文字写到 stdout，然后退出。快速问答、管道处理
--mode json每个事件输出一行 JSON（JSONL），然后退出。程序解析运行过程
--mode rpc从 stdin 读命令，持续输出响应和事件，直到关闭。其他程序长期控制 Pi

当 stdin 或 stdout 被重定向，而且没有指定 json 或 rpc 时，Pi 会自动进入 print 模式。

A.6 会话：继续、恢复、分叉

Pi 会自动保存会话，并按工作目录分组。退出后用下面的方式接着做：

会话相关的命令行选项与斜杠命令
命令作用
pi --continue（-c）继续当前目录最近的一次会话。
pi --resume（-r）打开会话选择器；按 Tab 可以显示其他目录的会话。
/new开始新会话。
/fork从某条较早的用户消息分出一个新会话。
/tree浏览会话树，跳到任意节点。
/compact压缩当前上下文，可附加压缩说明。
/name给会话设置显示名称。
pi --no-session使用不落盘的内存会话，退出即丢失。

A.7 斜杠命令、提示词模板与技能

在编辑框输入 / 会列出当前可用的命令。其中有三类是你自己可以添加的，它们解决的问题不同：

提示词模板

把一段常用提示词存成 .md 文件，变成 /命令。只做“复用文字”，没有额外脚本。

技能（Skill）

一个带 SKILL.md 的目录，可以附带脚本和参考资料。Pi 只先告诉模型技能的名字和描述，任务匹配时才读取完整说明。

扩展（Extension）

用代码注册工具、命令、事件钩子。能力最强，也最需要审查，见本节 B 部分。

提示词模板示例

~/.pi/agent/prompts/review.md
---
description: Review staged git changes
argument-hint: "[focus]"
---
Review the staged changes. Focus on ${1:-correctness, security, and error handling}.

保存后执行 /reload，就能用 /review 或 /review concurrency。文件名决定命令名；${1:-默认值} 表示第一个参数，缺省时使用默认值。

技能示例

pdf-tools/SKILL.md
---
name: pdf-tools
description: Extract text and tables from PDF files. Use when reading, converting, or inspecting PDFs.
---

# PDF tools

Read `references/formats.md` before converting a document. Run scripts relative to this skill directory.
写 description 的关键： 模型是根据描述决定要不要加载技能的。写清“做什么”和“什么时候用”。“帮助处理 PDF”这种描述路由信息太少，模型很可能不会加载它。想强制使用，输入 /skill:pdf-tools。SDK 宿主对技能的发现、过滤与注入，见 SDK 深入篇 03。

A.8 常用命令行选项

启动时可以指定的常见选项
选项作用
--model sonnet:high选模型，并用冒号后缀指定思考强度。
--models a,b限定 Ctrl+P 循环切换的模型范围。
--tools read,grep替换默认工具，只有列出的工具会声明给模型。
--no-builtin-tools关闭默认内置工具，保留扩展和自定义工具。
--session-dir <dir>指定会话的存放目录。
-n <name>启动时直接设置会话名称。
注意 --tools 是白名单： 默认工具是 read、bash、edit、write。一旦写了 --tools，没列出的内置工具就不会给模型。想保留默认工具又要加一个，用 --tools +名字 而不是重新列全部。

A.9 安全：先看清楚再放手

Pi 不会在每次工具调用前请求确认。 项目里的指令、被读取的文件内容、命令输出，都可能诱导模型做危险操作（提示注入）。项目信任（project trust）只决定是否加载项目级资源，不是安全边界。重要或无人值守的任务，应放在容器或虚拟机里运行，只暴露必要的文件和凭据。
练习 A · 把 Pi 用起来
  1. 在一个练习目录里运行 pi --print "这个目录里有什么文件？"，观察输出。
  2. 按 A.7 创建 review.md，执行 /reload，然后用 /review 调用它。
  3. 用 pi --tools read,grep 启动，让它修改一个文件，观察它能否完成。

检查点：你能说出 Enter 与 Alt+Enter 的区别，以及为什么 --tools 会“少了”默认工具吗？

进阶篇 B · 扩展机制全景

扩展：在 Pi 的生命周期里挂上钩子

第 7 课只讲了 tool_call 一个钩子。扩展实际上可以订阅很多事件，并注册工具、命令、快捷键，甚至注册模型供应商。这一节先给你一张完整地图。

B.1 扩展放在哪里

扩展的自动发现位置
位置作用范围
~/.pi/agent/extensions/*.ts全局，所有项目都生效
~/.pi/agent/extensions/*/index.ts全局，子目录形式
.pi/extensions/…仅当前项目；项目被信任后才加载
settings.json 的 extensions 字段额外指定的路径

扩展用 jiti 加载，TypeScript 不需要先编译。临时测试时可以用 pi -e ./my-extension.ts，不必放进目录。

扩展拥有你的全部系统权限。 它可以执行任意代码，所以只安装你信任的来源。

B.2 一个完整的最小扩展

~/.pi/agent/extensions/my-extension.ts
import { type ExtensionAPI, isToolCallEventType } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

export default function (pi: ExtensionAPI) {
  // 1. 订阅事件
  pi.on("session_start", async (_event, ctx) => {
    ctx.ui.notify("扩展已加载！", "info");
  });

  pi.on("tool_call", async (event, ctx) => {
    if (isToolCallEventType("bash", event) && event.input.command.includes("rm -rf")) {
      const ok = await ctx.ui.confirm("危险操作", "允许执行 rm -rf 吗？");
      if (!ok) return { block: true, reason: "用户拒绝" };
    }
  });

  // 2. 注册一个给模型用的工具
  pi.registerTool({
    name: "greet",
    label: "打招呼",
    description: "按名字向某人打招呼",
    parameters: Type.Object({
      name: Type.String({ description: "要打招呼的人" }),
    }),
    async execute(toolCallId, params, signal, onUpdate, ctx) {
      return {
        content: [{ type: "text", text: `你好，${params.name}！` }],
        details: {},
      };
    },
  });

  // 3. 注册一个给用户用的斜杠命令
  pi.registerCommand("hello", {
    description: "打个招呼",
    handler: async (args, ctx) => {
      ctx.ui.notify(`你好 ${args || "世界"}！`, "info");
    },
  });
}

这段代码展示了扩展最常用的三件事：订阅事件（pi.on）、注册能力（registerTool、registerCommand），以及通过 ctx.ui 与用户交互。

B.3 ExtensionAPI 的主要入口

扩展工厂函数拿到的 pi 对象能做什么
方法用途
pi.on(event, handler)订阅事件；返回的函数可以取消这一个订阅。
pi.registerTool(definition)注册模型能调用的工具（第 6 课的内容）。
pi.registerCommand(name, options)注册用户输入的斜杠命令。
pi.registerShortcut(key, options)注册键盘快捷键。
pi.registerFlag(name, options)注册 CLI 参数。
pi.registerProvider(name, config)动态注册或覆盖模型供应商（第 4 课的进阶版）。
pi.sendUserMessage() / pi.sendMessage()由扩展主动发消息给会话。
pi.exec(command, args)不经过 shell 直接执行命令。
注册工具可以在运行中进行： registerTool() 不只在加载时调用，也可以在 session_start 或命令处理函数里调用，新工具会立即出现，不需要 /reload。

B.4 一次 prompt 的完整事件顺序

这是整个扩展机制的核心。下面的顺序来自官方文档的生命周期说明：

一次用户输入从头到尾经过的事件
用户输入
 ├─ 扩展命令 /name        命中则直接执行，后面的 input 不再触发
 ├─ input                 可以 continue / transform / handled
 ├─ 展开 /skill:xxx 与 /template
 ├─ before_agent_start    可以注入消息、修改本轮系统提示词
 ├─ agent_start
 │   └─ turn_start                    （每一轮：一次模型请求 + 工具调用）
 │       ├─ context → context_with_system
 │       ├─ before_provider_headers → before_provider_request
 │       ├─ after_provider_response → provider_stream_event
 │       ├─ message_start / message_update / message_end
 │       └─ 每个工具调用：
 │            tool_execution_start
 │            tool_call            可以 block，或原地修改 input
 │            tool_execution_update
 │            tool_result         可以修改结果
 │            tool_execution_end
 │   └─ turn_end
 ├─ agent_end              ⚠ 不代表真正空闲：可能还会重试或处理排队消息
 ├─ agent_before_settle    最后一个可以追加条目、请求继续的点
 └─ agent_settled          最终状态，只通知，适合更新界面状态
别把 agent_end 当成“完成”： 它之后 Pi 仍可能自动重试、压缩上下文，或者处理排队的消息。需要“真正空闲”的通知，用 agent_settled。

B.5 事件的四种处理模式

同一个事件的处理方式取决于它属于哪一类。读文档时先确认这一点：

事件的几种模式
模式含义例子
通知返回值被忽略，只用来观察。agent_settled、thinking_level_select、provider_stream_event
原地修改直接修改传进来的对象。tool_call 的 event.input、before_provider_headers 的 headers
链式转换后面的处理器拿到前面返回的结果。context、tool_result（可返回部分字段）
门控返回特定结果就终止这次操作。input 返回 handled、tool_call 返回 block、session_before_compact 取消

这正是第 7 课的口诀在完整版里的样子：订阅（subscribe）只用来观察；扩展事件才能按契约影响流程。

B.6 tool_call：拦截与改参数

扩展里改写 bash 命令参数并拦截危险命令
import { isToolCallEventType } from "@earendil-works/pi-coding-agent";

pi.on("tool_call", async (event, ctx) => {
  if (isToolCallEventType("bash", event)) {
    // 原地修改参数：改动会真正作用到工具执行上
    event.input.command = `source ~/.profile\n${event.input.command}`;

    if (event.input.command.includes("rm -rf")) {
      return { block: true, reason: "危险命令", terminate: true };
    }
  }
});
修改参数之后不会重新校验。 如果你把 maxRows 改成了不合法的值，工具会直接收到它。所以关键限制仍然要在工具的 execute 里再检查一次（第 7 课已经强调过）。 另外 terminate: true 只对被 block 的调用生效，而且只有当这一批工具调用的最终结果全部是 terminating 时，Agent 才会提前停止——别把它当成单独生效的急停按钮。

B.7 input：在模型看到之前改写用户输入

把 “?quick …” 转换成简短回答的请求
pi.on("input", async (event, ctx) => {
  if (event.text.startsWith("?quick ")) {
    return { action: "transform", text: `请简短回答：${event.text.slice(7)}` };
  }
  if (event.text === "ping") {
    ctx.ui.notify("pong", "info");
    return { action: "handled" };       // 不调用模型
  }
  return { action: "continue" };        // 默认：原样放行
});

input 看到的是用户输入的原始文本，斜杠模板和技能还没有展开。返回值有三种：continue 放行，transform 改写后继续，handled 直接结束、不进入模型。

B.8 会话与资源相关的事件

常用的会话、资源事件
事件什么时候
session_start会话启动、加载、重载或切换后。event.reason 说明原因。
session_shutdown会话即将结束。用来关闭在 session_start 中打开的资源。
session_before_compact压缩前，可以取消或自定义压缩。
session_before_switch执行 /new 或 /resume 之前。
model_select用户切换模型时。恢复会话时不会触发，需在 session_start 里读取 ctx.model。
resources_discover会话启动后，扩展可以再添加技能、模板、主题的路径。
不要在扩展工厂函数里启动后台资源。 进程、socket、文件监听、定时器都应该延迟到 session_start 或真正需要它的时候启动，并在 session_shutdown 里关闭。因为工厂函数可能在根本没有会话的情况下运行。

B.9 写扩展的几条规则

  1. 先判断事件类型。只想观察，就用通知型事件；要干预，就用门控或转换型事件。
  2. 流式事件（如 message_update）里不要做慢操作。通知回调应保持轻量，慢的工作放进队列。
  3. 安全相关的门控要“失败即拒绝”。如果安全判断做不出来，就返回 block，而不是默认放行。
  4. 把 ctx.signal 传给你发起的请求。这样用户按 Escape 时，你的 fetch 也会被取消。
  5. 用 CONFIG_DIR_NAME 构造配置路径，不要硬编码 .pi。这样在改名的发行版里也能正常工作。
练习 B · 写你的第一个扩展
  1. 创建 ~/.pi/agent/extensions/hello.ts，在 session_start 时用 ctx.ui.notify 通知“扩展已加载”。
  2. 增加一个 input 处理器：把以 ?quick 开头的输入改写成“请简短回答：……”。
  3. 增加一个 tool_call 处理器：当 bash 命令包含 rm -rf 时，用 ctx.ui.confirm 询问，拒绝则 block。

检查点：你能说出 agent_end 和 agent_settled 的区别吗？为什么第 3 条要用 tool_call 而不是 subscribe？

进阶篇 C · 会话与上下文

会话是一棵树，上下文是它的一条分支

第 8 课讲了“每个用户一个 session”。这里讲另一面：一个会话里可以有多条分支，模型每次只看见当前这一条，而历史太长时，Pi 会把旧内容压缩成摘要。

C.1 续接与切换

不同入口决定会话在哪个工作目录里运行
入口工作目录
pi --continue当前目录
pi --resume、/resume、--session会话自己记录的目录，可能和当前目录不同
pi --fork当前目录，并生成一个新会话

每个会话都记录创建时的工作目录，而且之后不会改变。工具、@路径、项目配置都从这个目录解析。如果目录已经不存在（例如项目被改名），交互模式会问你：在当前目录继续、分叉成新会话，或取消。

用 /name 给会话起名字，用 /session 查看当前会话文件、ID、消息数、Token 用量和费用。

C.2 分支：/tree、/fork、/clone

Pi 把会话存成树。回到较早的位置并不会删除你离开的那条路，只是换了一条分支继续。

三种分支操作的区别
操作结果适合
/tree在同一个会话文件里移动相关的几种尝试想放在一起
/fork从较早的一条用户消息开新会话这条路应该变成独立的工作
/clone把当前分支复制成新会话想保留当前状态的一份副本

在 /tree 里选中一条用户消息，它的文字会回到编辑框，修改后提交就会形成一条新分支。离开一条分支时，Pi 可以把那条分支总结成一段摘要，附在你进入的分支上，保留有用的结论，却不带上全部消息。

C.3 上下文压缩（compaction）

自动压缩的触发条件可以用一行公式概括：

自动压缩的触发条件（来自官方压缩文档）
contextTokens > contextWindow - reserveTokens

默认 reserveTokens 是 16384。压缩的过程是：

  1. 从最新的消息往回数，累计到约 keepRecentTokens（默认 20000）为止，这里就是切分点；
  2. 切分点之前的消息交给模型生成结构化摘要，如果之前已经压缩过，会把旧摘要一起带上；
  3. 在会话里追加一条 compaction 条目，记录摘要和保留的起点；
  4. 之后发给模型的是：系统提示词 + 摘要 + 切分点之后的消息。
压缩不删除原始记录。 被摘要的消息仍然保存在会话文件里，只是不再发送给模型。导出或回溯时都还能看到。

切分点有规则：不会切在工具结果上，因为工具结果必须和它的工具调用放在一起。

C.4 手动压缩与设置

在 Pi 里手动压缩，可附加压缩重点
/compact
/compact 只保留数据库迁移相关的决定和未解决的问题
~/.pi/agent/settings.json · 压缩相关设置
{
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000
  }
}

关掉自动压缩（enabled: false）不会影响手动的 /compact。压缩失败时（例如服务暂时不可用），修好服务后再执行一次 /compact 即可。

C.5 扩展可以接管压缩

压缩前后都有事件：session_before_compact 可以取消压缩，或者自己提供摘要；压缩完成后是 session_compact，失败则是 session_compact_failed。这给了你在团队场景里定制摘要格式的机会，比如固定保留“已确定的决策”这一栏。

摘要是有损的。 模型可能遗漏细节。重要的约束（比如“不要改 API 返回格式”）最好同时写进 AGENTS.md，它每次都会加载，不会因为压缩而消失。
练习 C · 制造一次分支，再压缩一次
  1. 在一个会话里提出一个问题，得到回答后，用 /tree 回到前面的用户消息，换一种问法再提交。
  2. 用 /session 查看消息数，再执行 /compact，再看一次消息数和上下文用量。

检查点：压缩之后，原来的消息还在会话文件里吗？为什么切分点不能落在工具结果上？

进阶篇 D · 集成与对外接口

让别的程序用 Pi：JSON、RPC 与 MCP

第 9 课我们自己用 SSE 把 Agent 推给浏览器。Pi 其实已经提供了几种现成的对外接口，你要先选对方式，再动手。

D.1 先选接口

几种集成方式的区别（来自官方 RPC 文档）
方式进程边界控制方式适合
SDK同一进程直接调用 TypeScript 方法和事件Node.js / Bun 宿主，需要完整 API
RPC子进程stdin/stdout 上的 JSONL 命令、响应和事件其他语言、IDE、自定义界面
JSON 模式子进程，单次运行只输出事件流，结束即退出脚本解析一次运行的过程
print 模式子进程，单次运行只输出最终文字管道和简单脚本
Node.js 或 Bun 宿主，优先用 SDK。 子进程形式只在你需要进程隔离、或者宿主不是 JavaScript 时才值得。

D.2 JSON 模式：一次运行的事件流

终端：输出 JSONL 事件并保存
pi --mode json "Review this repository" > events.jsonl

输出的第一行是会话头，之后每行是一个事件。一次简单运行大致是这样的：

events.jsonl（节选，每行一个对象）
{"type":"session","version":3,"id":"uuid","timestamp":"2024-12-03T14:00:00.000Z","cwd":"/path"}
{"type":"agent_start"}
{"type":"turn_start"}
{"type":"message_update","assistantMessageEvent":{"type":"text_delta","contentIndex":0,"delta":"Hello"}}
{"type":"turn_end","message":{"role":"assistant"},"toolResults":[]}
{"type":"agent_end","messages":[],"willRetry":false}
{"type":"agent_settled","aborted":false}
解析 JSONL 不要用 readline。 Node 的 readline 还会把 U+2028、U+2029 当作换行，而它们在 JSON 字符串里是合法的。应该按字节或 UTF-8 流读取，只用 LF 切分。另外 stdout 只放协议数据，日志写到 stderr；读取 stdout 要持续进行，否则管道堵住会让 Pi 停下。

注意 agent_end 与 agent_settled 的区别（进阶 B 已经讲过）：前者只结束一轮低级运行，后者才表示 Pi 不会再自动继续。

D.3 RPC 模式：长期运行的子进程

终端：启动 RPC 子进程（不落盘）
pi --mode rpc --no-session

之后通过 stdin 发送 JSON 命令，每条命令可以带一个字符串 id，响应会带回同一个 id。命令处理是异步的，所以要按 ID 对应，而不是按顺序对应：

stdin 发送 / stdout 返回
{"id":"req-2","type":"prompt","message":"Review this repository"}
{"id":"req-2","type":"response","command":"prompt","success":true,"data":{"disposition":"started"}}
“prompt 成功”不代表模型已经回答完。 响应只说明这条消息被接受、排队或处理了。需要知道什么时候真正结束，要持续读取事件，并等待 agent_settled。如果响应的 disposition 是 "handled"，就根本没有开始新的运行，不要再等它。

如果你用 TypeScript 作为宿主，不必自己拼协议，可以使用导出的 RpcClient，它负责启动子进程、按 ID 配对响应，并把事件交给监听器：

src/rpc-demo.ts · 用 RpcClient 控制子进程
import { fileURLToPath } from "node:url";
import { RpcClient } from "@earendil-works/pi-coding-agent";

const client = new RpcClient({
  // cliPath 默认指向 pi 源码仓库里的 dist/cli.js，读者项目里并不存在。
  // 从 npm 安装时，用包导出的 ./rpc-entry 子路径——它就是给 RPC 子进程准备的入口。
  cliPath: fileURLToPath(import.meta.resolve("@earendil-works/pi-coding-agent/rpc-entry")),
  cwd: process.cwd(),
  args: ["--no-session"], // 与上面的手工示例一致：不落盘
});
await client.start();
try {
  const events = await client.promptAndWait("华东有哪些销售记录？");
  console.log(`收到 ${events.length} 个事件`);
} finally {
  await client.stop();
}

D.4 MCP：把外部服务变成工具

MCP（Model Context Protocol）让 Pi 接入别人写好的工具服务器，不用你自己在扩展里重写。它支持本地 stdio 和远程 HTTP 两种方式。在 SDK 会话里接入 MCP 的写法，见 SDK 深入篇 04。

终端：添加服务器、检查连接、启动 Pi
pi mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem .
pi mcp add docs --url https://example.com/mcp --bearer-token-env-var DOCS_TOKEN
pi mcp list
pi

服务器配置保存在 ~/.pi/agent/mcp.json（个人使用）或 .pi/mcp.json（项目共用，需要信任项目后才加载）：

~/.pi/agent/mcp.json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "."]
    },
    "docs": {
      "url": "https://example.com/mcp",
      "headers": { "Authorization": "Bearer ${DOCS_TOKEN}" },
      "description": "Search and read the product documentation"
    }
  }
}
  • 工具名会变成 mcp__<服务器名>__<工具名>，一眼就能看出来源。
  • command 只能是一个可执行文件，参数放在 args 里，不是一整条 shell 命令。
  • 凭据用 ${ENV} 引用环境变量，不要直接写进文件。
  • 远程服务支持 OAuth：只写 url，遇到需要登录时用 /mcp login 服务器名。
  • 在会话里用 /mcp 查看状态、重连、启用或禁用某个服务器；修改配置文件后执行 /reload。
MCP 服务器就是可执行代码。 它的工具拥有和 Pi 相同的权限。只添加你信任的服务器，项目级的 .pi/mcp.json 尤其要先审查。

D.5 和第 9 课的 SSE 方案怎么选

自己写 SSE 服务与使用 RPC 的取舍
问题自己写 SSE 服务（第 9 课）RPC 子进程
鉴权、用户隔离你自己负责，通常更灵活要自己在外层做，Pi 只是子进程
进程隔离与 Web 服务同进程Pi 在独立进程里，崩溃不拖垮宿主
会话多路复用你决定一个用户对应哪个 session每个子进程通常对应一个会话，需要自己管理进程池
开发量要自己拼事件、断线取消协议已定义好，但要管理子进程生命周期

无论哪种方式，多用户场景下的隔离和授权都是你的责任。Pi 的协议不替你做这些。

练习 D · 用 JSON 模式读一次运行
  1. 运行 pi --mode json "这个目录里有什么？" > events.jsonl。
  2. 写一个小脚本，只用 LF 切分，统计每种 type 出现的次数。
  3. 再用 pi --mode rpc --no-session 启动，手动发一条带 id 的 prompt，找到对应的响应。

检查点：你能说出 disposition 为 "handled" 时为什么不应该等 agent_settled 吗？

进阶篇 E · 配置、模型与环境

Pi 的配置分两层：用户级和项目级

大多数“为什么 Pi 行为不一样”的问题，答案都在配置文件里。这一节帮你知道每个文件管什么，以及谁覆盖谁。

E.1 用户目录与项目目录

常用配置文件（节选，完整列表见官方配置文档）
路径作用
~/.pi/agent/settings.json用户级设置，包括偏好、默认值、资源路径
~/.pi/agent/models.json兼容的模型服务端点与模型覆盖
~/.pi/agent/auth.json通过 /login 保存的 API Key 与 OAuth 凭据
~/.pi/agent/mcp.json所有项目可用的 MCP 服务器
~/.pi/agent/keybindings.json自定义快捷键
~/.pi/agent/AGENTS.md跨目录生效的个人说明
~/.pi/agent/SYSTEM.md替换 Pi 默认的系统提示词
~/.pi/agent/APPEND_SYSTEM.md在默认系统提示词后追加说明
.pi/settings.json、.pi/mcp.json、.pi/extensions/ 等项目级配置，项目被信任后才加载

几条规则：

  • 配置目录默认是 ~/.pi/agent，可以用环境变量 PI_CODING_AGENT_DIR 改。
  • 项目的 SYSTEM.md 优先于用户目录里的同名文件，两者不会合并。
  • AGENTS.md 之类的上下文文件不需要项目信任也会加载，所以把它当作不可信的输入对待。
  • 修改设置后执行 /reload，或者用 /settings 在界面里改常用项。

E.2 常用设置

settings.json · 一个典型的个人配置片段
{
  "defaultTools": ["read", "bash", "edit", "write"],
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000
  }
}

具体有哪些选项、默认值是多少，以官方的 settings.md 为准。前面讲过的 compaction 就是其中一组。

E.3 模型：先 /login，再 /model

对内置支持的服务商，两步就够了：/login 选择服务商并登录，/model 选模型。在 /model 里按 Ctrl+S 可以把它设为新会话的默认模型；Ctrl+P 在已配置的模型之间循环。

凭据的查找顺序是：命令行 --api-key → auth.json → models.json 里的 apiKey → 服务商的环境变量。CI 之类不想写入凭据的环境，直接用环境变量就行。

E.4 接入兼容的本地或私有端点

如果服务端实现的是 OpenAI、Anthropic 或 Google 兼容接口，就在 models.json 里声明它：

~/.pi/agent/models.json · 本地 Ollama 示例
{
  "$schema": "https://pi.dev/schemas/models.schema.json",
  "providers": {
    "ollama": {
      "baseUrl": "http://localhost:11434/v1",
      "api": "openai-completions",
      "apiKey": "ollama",
      "models": [
        { "id": "qwen2.5-coder:7b" }
      ]
    }
  }
}

这里 apiKey 写的是一个占位值，Ollama 会忽略它。真正需要密钥的地方，用 $变量名 或 ${变量名} 引用环境变量，第 4 课的 $MY_COMPANY_API_KEY 就是这种写法。!命令 形式则会在请求时运行命令取得密钥，且不缓存。

E.5 本地模型：llama.cpp

如果你有 GGUF 格式的本地模型，Pi 可以直接连接 llama.cpp 的路由服务器：路由器发现模型并按需加载，/llama 管理它，/model 选择已加载的模型。具体的服务器启动和模型目录结构，见官方的 llama-cpp.md。

练习 E · 把个人偏好和项目说明分开
  1. 在 ~/.pi/agent/AGENTS.md 写一条个人偏好（例如“回答用中文”）。
  2. 在一个项目的根目录写一个 AGENTS.md，写这个项目的约定。
  3. 在两个目录里分别问同一个问题，观察回答风格是否都受到了影响。

检查点：如果把 API Key 同时写进 auth.json 和环境变量，哪一个会先被使用？

进阶篇 F · 安全与上线

把 Agent 放进边界里运行

Pi 默认以你的系统用户身份运行，能读写你能访问的所有文件，并且不会为每次工具调用请求确认。这一节讲清楚边界在哪里，以及怎样把它收紧。

F.1 威胁来自哪里

  • 提示注入：文件内容、网页、命令输出、项目指令都可能夹带诱导模型执行危险操作的文字。
  • 模型的错误判断：它可能删错文件、运行错误的命令，或者把数据发到不该去的地方。
  • 扩展、技能、MCP 服务器：它们作为 Pi 的一部分运行，权限与 Pi 相同。
查看对话记录、使用项目信任，都不是安全边界。 它们只能帮你发现问题，不能阻止问题发生。真正的边界来自操作系统、容器或虚拟机。

F.2 项目信任

当一个目录含有 .pi/settings.json、.pi/mcp.json、.pi/extensions、.pi/skills、.pi/prompts 等项目资源时，Pi 会先询问是否信任。信任之后，这些项目资源才会加载，包括项目扩展和项目里的 MCP 服务器。

信任决定的来源，按优先级排列
顺序来源
1命令行的 --approve / --no-approve
2用户级或命令行扩展的 project_trust 事件
3保存过的决定（/trust 写入 ~/.pi/agent/trust.json）
4全局设置 defaultProjectTrust，默认 "ask"

在打印、JSON、RPC 模式下没有交互提示。如果自动化脚本需要加载项目资源，要显式加上 --approve。

F.3 选择隔离方式

几种常见的隔离方式（节选）
方式Pi 运行的位置适合
直接运行你的系统用户只能靠专用账号收窄权限，共享系统和网络
普通 Docker 容器容器内，包括内置工具和扩展最直接的本地边界，适合大多数人
托管沙箱（如 Docker Sandboxes、OpenShell）受管理的沙箱需要更细的网络和凭据策略
扩展方式（如 Gondolin）宿主机，只隔离内置工具只想隔离命令执行，其他扩展仍在宿主机上

隔离的范围取决于你暴露了什么。把整个 ~/.pi/agent 挂进容器，等于把凭据和会话都交出去了；读写挂载的工作目录，改动也会直接写回宿主机。

F.4 一个最小的 Docker 运行方式

Dockerfile.pi
FROM node:24-bookworm-slim

RUN apt-get update \
  && apt-get install -y --no-install-recommends bash ca-certificates git ripgrep \
  && rm -rf /var/lib/apt/lists/*
RUN npm install -g --ignore-scripts @earendil-works/pi-coding-agent

WORKDIR /workspace
ENTRYPOINT ["pi"]
终端：只挂载当前工作目录，配置放在命名卷里
docker build -t pi-sandbox -f Dockerfile.pi .
docker run --rm -it \
  -e ANTHROPIC_API_KEY \
  -v "$PWD:/workspace" \
  -v pi-agent-home:/root/.pi/agent \
  pi-sandbox

这里 -v pi-agent-home:/root/.pi/agent 用的是独立的命名卷，而不是宿主机的 ~/.pi/agent。进入 Pi 后执行 !pwd，应该看到 /workspace，说明挂载正确。

F.5 上线前的检查清单

  1. Pi 只能访问任务需要的文件和服务。
  2. 凭据用环境变量或短期令牌，不写进仓库、截图或分享的会话。
  3. 网络访问按需开放，任务不需要联网就关掉。
  4. 扩展、技能、MCP 服务器都审查过来源和代码。
  5. 重要改动前有备份或版本控制，结果在应用到其他系统前先看 diff。
  6. 导出或分享会话前先检查，里面可能包含文件内容、命令输出和曾经暴露的凭据。
练习 F · 画出你的边界

对你计划运行 Pi 的任务，回答下面三个问题：

  1. Pi 需要读写哪些目录？哪些绝对不能让它碰到？
  2. 它需要哪些凭据？能否换成只读或短期的？
  3. 它需要联网吗？如果不需要，你打算怎样关掉网络？

检查点：按这三点写出的挂载或权限方案，能否在不依赖“提示词写得好”的前提下成立？

学 Pi Agent 的目标不是背 API，而是知道每一层负责什么、出问题该去哪一层找。
