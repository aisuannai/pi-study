开始前 · 先建立正确的预期

你不需要先学完 TypeScript

学 Agent 时，只需要先认得常见写法。遇到类型标注，把它当“说明这是什么”；遇到异步， 先记住“要等它完成”。本教程会在代码旁翻译这些符号，不要求你背语法书。

1看懂一点

认出变量、函数、对象和 await，知道每段代码大概负责什么。

2跑起来

让 Agent 回答一句话，看到输出，并理解模型、会话、事件的分工。

3改得动

能换提示词、添加安全的业务工具，再根据自己需求继续扩展。

安全提醒： 模型会说错，提示词也不是权限系统。真正的数据权限必须在你的工具实现和后端检查，不能只靠“请不要越权”的提示词。

第 01 课 · 准备环境

先搭一个能重复做实验的小工作台

Pi Agent 是 Node.js / TypeScript SDK。我们先把版本钉住，让“教程代码”和“本机安装的代码”说同一种语言。

1.1 检查 Node.js 和项目配置

Pi Agent 1.6.1 要求 Node.js 22.19.0 或更新版本。项目要用 ESM，所以 package.json 里要有 "type": "module"。

终端：创建工作台并安装依赖

cd pi-agent-learning
npm init -y

npm install --ignore-scripts @earendil-works/pi-coding-agent@1.6.1 typebox@1.3.27
npm install -D typescript@^5.9 @types/node@^24

新建 src/hello.ts 保存后，用 node src/hello.ts 运行；用 npx tsc --noEmit 做静态类型检查。Node 22.19+ 能直接擦除本教程用到的 TypeScript 类型标注，不代表它会替你做 TypeScript 类型检查。

第 02 课 · 第一个 Agent

先让它回答一句话

最小闭环需要四样东西：可用模型、会话、一次提问，以及一个把生成文字显示出来的事件监听器。

主线项目 · DataAgent 第 1 步： 从这一课起，代码都往同一个文件里长：src/data-agent.ts。本课的 hello.ts 就是它的雏形——一个“裸 prompt”的 Agent。先把它复制过去，后面每课给它加一层能力。
src/hello.ts · 可直接作为第一个实验
import {
  createAgentSession,
  ModelRuntime,
  SessionManager,
} from "@earendil-works/pi-coding-agent";

// 1. 读本机模型与认证配置
const modelRuntime = await ModelRuntime.create();
const choices = await modelRuntime.getAvailable();
const model = choices[0];

if (!model) {
  throw new Error("没有可用模型：请先配置 Provider 和 API Key");
}

// 2. 创建一段对话；inMemory 表示历史只存在内存里，不写会话文件
const { session } = await createAgentSession({
  model,
  modelRuntime,
  sessionManager: SessionManager.inMemory(),
});

// 3. 订阅文字增量
const unsubscribe = session.subscribe((event) => {
  if (
    event.type === "message_update" &&
    event.assistantMessageEvent.type === "text_delta"
  ) {
    process.stdout.write(event.assistantMessageEvent.delta);
  }
});

try {
  await session.prompt("用三句话介绍你自己。");
  process.stdout.write("\n");
} finally {
  unsubscribe();
  session.dispose();
}
读这段代码modelRuntime 管模型；session 管这一段对话；subscribe 负责“看过程”；prompt 负责“开始做”。SDK 会话默认是持久化的，每次 createAgentSession() 都会生成一个会话文件；示例传 SessionManager.inMemory()，反复运行不会在磁盘上堆积文件。

逐段翻译：程序是怎么走下去的

把最小示例翻译成不带术语的话
代码人话
await ModelRuntime.create()读配置，准备和模型沟通的运行时。
await modelRuntime.getAvailable()询问当前有哪些模型可以用；await 表示等结果回来再继续。
if (!model)如果列表里没有选出模型，就先报错停止；不要带着空模型继续。
createAgentSession(...)用选中的模型创建一段新的 Agent 对话；不传 sessionManager 时默认持久化到会话文件。
session.subscribe(...)登记一个监听函数；Pi 发来事件时运行它。
event.type === "message_update"只处理“消息正在变化”这一类事件。检查后，TypeScript 才允许安全读取相应字段，这叫类型收窄。
await session.prompt(...)把问题交给 Agent，并等待这次处理完成。
unsubscribe(); session.dispose()停止收事件，再结束这段会话运行时。

把几个容易混淆的角色分开

ModelRuntime

像模型通讯录和钥匙管理员：知道有哪些模型、要用什么认证。

AgentSession

像一个正在进行的对话桌面：保存消息、当前模型、工具和会话状态。

prompt()

给这个对话桌面一项任务，然后等待这轮处理完成。

subscribe()

旁边的观察窗：收到文字、工具开始/结束等事件。

为什么有 finally？ 就算模型请求失败或你中途取消，清理监听器、释放 session 仍会执行。dispose() 不是“保存按钮”，会话历史的保存由 SessionManager 负责。 如果你只想要“最终回答”而不关心流式过程，官方最小示例用 session.getLastAssistantText() 一行就能取到，连订阅都可以省掉。
Node 与 TypeScript 是两件事： node src/hello.ts 负责运行；tsc --noEmit 负责检查类型。Node 不会因为你写了 : string 就替你检查变量类型。
练习 2 · 做两个小改动
  1. 把问题改成你自己感兴趣的内容。
  2. 先临时注释掉 message_update 判断，看看事件里除了文字之外还出现了什么。
  3. 再临时注释掉“取消订阅并清理 session”的代码，想想连续运行很多次可能留下什么。

检查点：你能指出哪一行发问、哪一行输出增量、哪两行负责清理吗？

踩坑实验 · 不 await 的第二个 prompt 会怎样？

把提问部分改成连续两次调用，但第一个不加 await：

session.prompt("第一个问题");
await session.prompt("第二个问题");

第二个调用会直接抛错：Agent is already processing. Specify streamingBehavior ('steer' or 'followUp') to queue the message.

这不是 bug，是设计：同一个会话同时只有一个 run，流式输出期间的第二个 prompt 必须说明是“插话”还是“排队”，Pi 拒绝替你猜。真正的修法在第 09 课 9.1——先记住这个报错，它是 Web 服务里最常见的第一个异常。

第 03 课 · 看懂 Agent 的引擎

Agent 不是一次 API 请求，而是一圈“想—做—看”

如果模型只回答文字，一轮就结束；如果它决定使用工具，Pi 会运行工具，把结果放回对话，再问模型下一步。

主线项目 · DataAgent 第 2 步： 给 data-agent.ts 装上“行车记录仪”：把订阅回调改成 console.log(new Date().toISOString().slice(11, 23), event.type)， 跑一次带工具的任务，把事件时间线存下来——这是高级篇 H 观测能力的种子。

从这段动画里记住的知识点

四层心智模型

agent 是一次完整任务，turn 是一次模型请求加它引发的工具执行，message 是一条消息，message_update 只出现在 assistant 消息的 start 与 end 之间。有工具调用，就至少两轮。

三类流式子事件

thinking_* 是推理，text_* 是正文，toolcall_* 是参数 JSON 分片。块的序号看 contentIndex；start/end 可能交错，别靠事件顺序猜结构。

半截 JSON 是常态

toolcall_delta.delta 只是参数的一小片，单独 JSON.parse() 必失败；完整参数在 toolcall_end.toolCall.arguments 里，或自己累积。

stopReason 定下一步

toolUse → 执行工具再来一轮；stop → 正常说完；length → 所有 toolCall 直接判失败；error/aborted → 立即收尾。

“结束”有三个层次

一条消息结束是 message_end，一轮结束是 turn_end，整个任务结束看 agent_settled。agent_end 之后还可能自动重试（willRetry）。

成败在 tool_execution_end

工具的 result、isError、durationMs 只在结束事件里有；tool_execution_update 只是流式输出。

速查 · 完整事件序列（1.6.1 实测）

这是动画播放的全部 23 步，做完练习 3 之后再回来对照：

事件序列 · session.prompt("我的IP是多少")
agent_start
turn_start                          ← 第 1 轮 = 第 1 次模型请求
  message_start/end  role:system    ← 工具声明消息，工具集变化时才发
  message_start/end  role:user      ← 传入的 prompt，成对出现
  message_start      role:assistant
    message_update   thinking_start → delta×N → thinking_end
    message_update   toolcall_start → delta×N → toolcall_end
  message_end        role:assistant  stop=toolUse
  tool_execution_start   bash { command: "ip addr" }
  tool_execution_update×N
  tool_execution_end     { result, isError, durationMs }
  message_start/end  role:toolResult
turn_end { message, toolResults }

turn_start                          ← 第 2 轮
  message_start      role:assistant
    message_update   text_start → delta×N → text_end
  message_end        role:assistant  stop=stop
turn_end { message, toolResults: [] }

agent_end { messages, willRetry }
agent_settled { aborted }           ← 真正的终态

把词汇放进这段动画里

  • Run：一次用户任务的完整处理。可能包含重试或多个 turn。
  • Turn：一次模型请求和这次回复里的工具调用处理。
  • Message：对话中的一条消息，比如 user、assistant 或 tool result。
  • Event：Pi 对外发出的“刚才发生了什么”的通知或扩展钩子。
  • Transcript：会话里的消息与结构化记录；不是单纯的屏幕输出。

源码放大镜：subscribe 为什么是“观察窗”

在 Pi 1.6.1 的 AgentSession._emit() 里，事件广播的核心可以缩小成下面几行：

源码摘录 · agent-session.js · AgentSession._emit(event)
_emit(event) {
  for (const l of this._eventListeners) {
    l(event);
  }
}
白话解释Pi 把事件交给每个 listener；它不收集 listener 的返回值来决定是否执行工具。这里的调用是同步发生的，所以 listener 里做大量同步计算会拖慢派发；数据库等慢工作应放进受控队列，不要阻塞事件回调。

对应源码位置：packages/coding-agent/src/core/agent-session.ts，搜索 _emit。这就是为什么宿主层的订阅器适合显示文字、工具状态和轻量日志，而“拦截工具”要使用扩展层的决策钩子。

源码阅读技巧： 先在类型定义里找事件结构，再在发出事件的地方找调用点，最后回到 SDK 入口看是谁把它们连起来。不要从一个几千行文件第一行开始硬读。 想沿 prompt() 一路走到第一个字符上屏，见高级篇 J 的完整路径——那里把本课的鸟瞰图逐行走完。

run 结束，不一定代表真的闲下来了

Pi 可能在一次 run 后继续重试、压缩上下文，或处理排队消息。用 agent_end 判断最终空闲会过早； 若需要真正的结束通知，看 agent_settled。在 HTTP handler 里，通常等待 await session.prompt(...) 也能确定这次调用已返回。

练习 3 · 画出你自己的事件时间线

把监听器临时改成只打印 event.type，问一个需要工具的问题。按先后顺序写下你看到的事件。

检查点：找找 agent_start、turn_start、message_update、工具事件和 agent_settled 的相对顺序。不同请求和模型可能发出不同数量的流事件。

踩坑实验 · 在订阅回调里忙等 500 毫秒会怎样？

在 subscribe 回调里加一段同步忙等（比如空转循环半秒），再问一个长回答的问题。

你会看到：文字流变成一顿一顿的，整体完成时间明显变长。

为什么：_emit 是同步循环（本课的源码摘录），每个事件都要等你的回调跑完才轮到下一个订阅者——流式事件一多，慢回调就成了节流阀。

修法：回调只做轻活；重活先入队、异步处理，或移到扩展通道（进阶篇 B.9 的规则 2）。

第 04 课 · 模型与认证

让 Agent 找到模型，也把钥匙放好

模型定义回答“调用谁”，认证回答“凭什么调用”。它们有关联，但不是同一件事。

主线项目 · DataAgent 第 3 步： 把 choices[0] 换成精确选择：modelRuntime.getModel("anthropic", "claude-opus-4-5")， 选不到就带着清晰的报错退出。生产代码不靠“第一个可用”碰运气。

4.2 三个 API 分别在干什么

ModelRuntime.create()

载入模型与认证配置；默认不是“马上向模型发送问题”。

getAvailable()

询问目前有哪些有认证、可用来聊天的模型。

setRuntimeApiKey()

在运行期间注入 Key；适合服务端按登录用户取凭据的进阶场景。

练习 4 · 没有可用模型时，先排查什么？
  1. Provider 名、api、模型 ID 和 baseUrl 是否对。
  2. 环境变量有没有在启动 Node 的同一个终端里设置。
  3. Key 是否有效、服务地址是否能访问；不要先猜代码 API 写错。
踩坑实验 · 明明设了 Key，为什么还是“没有可用模型”？

在终端 A 里设置环境变量（PowerShell：$env:MY_COMPANY_API_KEY = "sk-..."），然后在终端 B 里启动 node src/data-agent.ts。

你会看到：getAvailable() 返回空，报“没有可用模型”。

为什么：环境变量属于进程环境，只在设置它的那个终端及其子进程里可见。官方排查文档专门列了这条：“环境变量必须存在于启动 Pi 的那个进程里”。

修法：在同一个终端设置后再启动；或写进 models.json 的 $VAR 引用，并保证启动脚本注入了它。

第 05 课 · 系统提示词

把通用 Agent 变成你需要的角色

提示词告诉模型“做事时遵循什么规则”。固定的人设可以在会话资源加载时设置；动态、每次请求不同的信息需要更仔细地安排注入位置。

主线项目 · DataAgent 第 4 步： 把本课的四条角色规则搬进 data-agent.ts 的 systemPromptOverride， 尤其保留“查询没有结果就明确说不知道”——它是高级篇 H 评测用例的判分依据。
用 ResourceLoader 设置静态人设
import {
  DefaultResourceLoader,
  getAgentDir,
} from "@earendil-works/pi-coding-agent";

const resourceLoader = new DefaultResourceLoader({
  cwd: process.cwd(),
  agentDir: getAgentDir(),
  systemPromptOverride: () => [
    "你是一个企业数据分析助手。",
    "只根据查询工具返回的数据给出数字。",
    "没有查到的数据要明确说不知道。",
    "先给结论，再给简短依据。",
  ].join("\n"),
  appendSystemPromptOverride: () => [],
});

await resourceLoader.reload();
它做了什么systemPromptOverride 覆盖基础提示词（base 来自 SYSTEM.md，文件不存在时为 undefined）；reload() 让 loader 完成资源加载；再把这个 loader 交给 createAgentSession。

提示词来源的心智模型

提示词不是权限控制。 比如“用户只能看销售部数据”，不仅要写在提示词里，还要在工具执行时从认证上下文确认 userId 和部门，并对查询条件做服务端限制。

ResourceLoader 是什么：会话的资源装配器

DefaultResourceLoader 负责把散落在磁盘上的“会话资源”发现、合并、校验成一份快照： 系统提示词、追加提示词、各级 AGENTS.md、技能（skills）、提示词模板、主题和扩展。 createAgentSession 拿到快照后，再用它和工具声明拼出真正发给模型的系统提示词。

有 customPrompt（来自 systemPrompt 或 systemPromptOverride）时，它就是 <preamble> 段， 并且内置的 <tools>、<rules>、<docs> 三段不会生成； 没有时才回退到 Pi 内置的编码代理提示词。其余段落两种情况都会拼：

踩坑实验 · 把当前时间写进系统提示词，会发生什么？

在 systemPromptOverride 里拼上 当前时间：${new Date().toISOString()}，连发两次相同的问题。

为什么：系统提示词是请求前缀的第一行，时间一秒一变，提示词缓存的前缀永远对不上（高级篇 G.2 的“前缀稳定才省钱”）。

工具是模型提议、你的程序执行

模型不能凭空访问你的数据库。你把可用动作定义成工具，模型选择工具并填写参数，Pi 校验参数后调用你的 TypeScript 函数。

6.1 定义一个安全的只读查询工具

src/tools/query-sales.ts · 教学用内存数据
import { Type } from "typebox";
import { defineTool } from "@earendil-works/pi-coding-agent";

const sales = [
  { region: "华东", product: "键盘", amount: 1200 },
  { region: "华南", product: "鼠标", amount: 800 },
  { region: "华东", product: "显示器", amount: 3200 },
];

export const querySalesTool = defineTool({
  name: "query_sales",
  label: "查询销售记录",
  description: "按地区查询示例销售记录。只读，不会修改数据。",
  parameters: Type.Object({
    region: Type.String({
      description: "地区名称，例如：华东",
    }),
    maxRows: Type.Optional(
      Type.Number({
        description: "最多返回几条，至少为 1",
        minimum: 1,
      }),
    ),
  }),
  async execute(_toolCallId, params, signal) {
    if (signal?.aborted) {
      return {
        content: [{ type: "text", text: "查询已取消。" }],
        details: { count: 0 },
        isError: true,
      };
    }

    const maxRows = Math.min(params.maxRows ?? 10, 20);
    const rows = sales
      .filter((row) => row.region === params.region)
      .slice(0, maxRows);

    if (rows.length === 0) {
      return {
        content: [{ type: "text", text: `没有找到 ${params.region} 的记录。` }],
        details: { count: 0 },
      };
    }

    return {
      content: [{
        type: "text",
        text: JSON.stringify(rows, null, 2),
      }],
      details: { count: rows.length },
    };
  },
});

name 和 description

名字是程序标识；描述要让模型明白何时用、做什么、不做什么。

parameters

TypeBox 描述输入形状。Pi 验证工具参数，再把类型推导传给 params。

execute

这里才是真正的业务代码。数据库权限检查、数据范围限制也必须在这里落实。

content 和 details

content 给模型看；details 可留给 UI、日志或程序处理。

当前版本的重要更新： Pi 1.6.1 的工具结果支持 isError: true。失败可以抛异常，也可以返回错误结果；普通“没有匹配数据”通常不是程序错误，应返回正常结果，不要把它标成失败。
TypeBox 的边界： Pi 用 JSON Schema 兼容的校验器处理工具参数。基础的 Type.String、Type.Number、Type.Object 适合教学；不要假设 TypeBox 所有运行时扩展特性都一定会执行。

踩坑实验 · 一个不检查 signal 的慢工具，abort 得动吗？

在 execute 里加一个 10 秒的忙等循环（不看 signal），并在 prompt 之前安排 500 毫秒后取消：setTimeout(() => void session.abort(), 500)。

你会看到：取消“卡住”了——工具照样跑满 10 秒，tool_execution_end 迟迟不来。

为什么：abort() 只负责发出信号；源码里的 prepareToolCall 只能在“开始执行前”替你拦，执行中的取消要靠工具自己配合。

修法：长循环每轮检查 signal?.aborted；网络请求传 { signal }；取消后返回“已取消”的结果。

7.1 1.6.1 的工具事件时序

真实源码也按这个顺序组织。注意：Agent 核心层的默认 toolExecution 是 "parallel"，同一轮里有多个工具调用时，各工具的事件会交错出现；只有配置为 "sequential"，或工具自己声明 executionMode: "sequential" 时，才走下面这条顺序路径。下面是 Pi 1.6.1 中顺序工具执行路径的缩小摘录（省略错误处理和并行执行分支）：

源码摘录 · agent-loop.js · executeToolCallsSequential()
await emit({
  type: "tool_execution_start",
  toolCallId: toolCall.id,
  toolName: toolCall.name,
  args: toolCall.arguments,
});
const preparation = await prepareToolCall(
  currentContext, assistantMessage, toolCall, config, signal,
);

let finalized;
if (preparation.kind === "immediate") {
  finalized = {
    toolCall,
    result: preparation.result,
    isError: preparation.isError,
  };
} else {
  const executed = await executePreparedToolCall(
    preparation, signal, emitToolExecutionUpdate(toolCall, emit),
  );
  finalized = await finalizeExecutedToolCall(
    currentContext, assistantMessage, preparation, executed, config, signal,
  );
}

await emitToolExecutionEnd(finalized, emit);
const toolResultMessage = createToolResultMessage(finalized);
await emitToolResultMessage(toolResultMessage, emit);
读懂关键点tool_execution_start 在 prepareToolCall 前；扩展的 tool_call 安检发生在准备阶段；如果结果是 immediate（例如被拦截），就不会进入 executePreparedToolCall。

7.2 写一道工具调用的安全门

扩展里的 tool_call 钩子
import type { ExtensionFactory } from "@earendil-works/pi-coding-agent";

const limitGuard: ExtensionFactory = (pi) => {
  pi.on("tool_call", (event) => {
    if (event.toolName !== "query_sales") return;

    const maxRows = event.input.maxRows;
    if (typeof maxRows === "number" && maxRows > 20) {
      return {
        block: true,
        reason: "单次最多查询 20 条，请缩小范围后重试。",
      };
    }
  });
};

事件 tool_call 的参数类型里可能装着任意 JSON 值，所以示例先用 typeof 检查，不假设模型一定遵守类型。真正的硬上限仍建议在工具 execute 内再次检查。

7.3 每个事件有自己的契约

tool_call

工具执行前检查；可以返回 block: true 拦截。要改参数时，原地修改 event.input，而不是返回新参数。

context

每次模型请求前处理对话消息；这个事件里的 messages 不包含系统提示词。

context_with_system

需要查看或转换完整上下文（含 system message）时使用；返回的消息列表会原样发给模型，必须保留下标 0 的 system message——它承载系统提示词和工具声明，删掉会直接报错。

tool_result

执行之后观察或改写返回给模型的结果；不要与“工具开始执行”混为一谈。

审计时序别踩坑： 被 block 的工具也会有 tool_execution_start 和带错误结果的 tool_execution_end；它不代表业务 execute() 真的跑过。 需要统计实际执行次数时，记录 tool_call 是否被拦截，或在工具内部打审计记录。

踩坑实验 · 为什么我在 subscribe 里 return 了 block，工具还是跑了？

把安全门代码从扩展 pi.on("tool_call") 挪进 session.subscribe 回调，返回 { block: true, reason: "超限" }，再请求 999 条。

你会看到：拦截完全不生效，工具照常执行，返回值像被扔掉了一样。

为什么：subscribe 是观察通道，_emit 根本不收集返回值（第 03 课的源码摘录）；门控契约只存在于扩展钩子里，由 agent 的 beforeToolCall 读取。

修法：拦截逻辑放回扩展。顺带观察时间线——被拦截的调用照样有 tool_execution_start 和带错误的 tool_execution_end（高级篇 J.5 的四道关卡）。

第 08 课 · 会话、记忆与隔离

“记住聊天”不等于“所有用户共用一份状态”

一个 session 是一段对话。多轮聊天需要复用同一个用户的会话；不同用户要有不同会话和授权上下文。

主线项目 · DataAgent 第 7 步： 把 data-agent.ts 改造成工厂：function createUserSession(userId: string)， 每个用户一份 inMemory 会话，并把 userId 写进该用户的系统提示词。第 09 课的 Web 服务直接拿它当路由表。

SessionManager.inMemory()

适合实验或由应用自己保存对话；进程重启后，内存中的历史会消失。

默认会话管理

适合本地单用户体验，但 Web 多用户通常要把用户 ID、会话 ID 与存储记录关联起来。

AgentSessionRuntime

进阶的会话生命周期工具，支持替换/恢复/分叉等操作；入门先理解 session，再学它。

服务端设计原则： 每个请求先认证用户，再按 userId 找到其 session；工具每次执行都确认用户可以访问该数据。 不能只把 userId 拼进提示词就认为权限隔离完成了。
练习 8 · 找出这个设计的 bug

服务端只有一个全局变量 let session，所有用户登录后都共用它。会发生什么？

答案方向：历史可能串线、并发 prompt 冲突、用户上下文或授权信息可能混用。至少要按已认证用户隔离 session 和用户上下文。

踩坑实验 · 亲眼看见会话串台

用一个全局 session 模拟两个用户：先以用户 A 发“我叫小明，我最喜欢键盘”；等回答完，再以用户 B 发“我叫小红。请问我叫什么名字？我最喜欢什么？”

你会看到：Agent 很可能答出“小明”和“键盘”——用户 B 读到了用户 A 的对话。

为什么：session 是唯一的对话状态容器，历史、身份、上下文全在里面；共享 session 就等于共享记忆。

再进一步：不等回答完就连发两条 prompt，还会撞见第 02 课踩坑实验里那个 "already processing" 报错——隔离和并发是同一个问题的两面。

第 09 课 · 从终端走向 Web

SSE 是把 Agent 事件送到浏览器的一条管道

Pi SDK 负责 Agent 和事件；你的 Web 服务负责 HTTP、认证、会话路由和把事件编码成 SSE。

9.1 会话正在忙时：steer、followUp 与 abort

上面的骨架有一个隐藏前提：调 session.prompt() 时会话是空闲的。SDK 的规则是， 会话正在流式输出时再次调用 prompt()，必须说明这条消息是“插话”还是“排队追加”， 否则 Pi 会直接拒绝这次调用，而不是替你猜。Web 服务里用户连发两条消息是常态，所以要显式处理：

src/chat-queue.ts · 按会话状态路由用户消息
// 用生命周期事件维护“是否正在运行”的标志
let running = false;
session.subscribe((event) => {
  if (event.type === "agent_start") running = true;
  if (event.type === "agent_settled") running = false; // 真正空闲，见进阶篇 B
});

async function enqueue(message: string) {
  if (!running) {
    await session.prompt(message);                  // 空闲：开始一次新的运行
    return;
  }
  const disposition = await session.steer(message); // 插话：当前回复结束后立即生效
  // 想排到整个任务之后再处理，改用 await session.followUp(message)
  // 返回 "queued" 表示已排队；"handled" 表示被扩展消费，不要再等它产生输出
  if (disposition === "handled") return;
}
三个配套方法： session.abort() 停止当前操作并等会话空闲——SSE 断连时调用它，而不是直接扔掉 session； session.waitForIdle() 只等不取消；插话和排队的送达节奏还可以用设置里的 steeringMode / followUpMode 调整。
上线前的安全检查： 认证、速率限制、并发控制、消息长度、用户数据隔离、工具权限、断连取消和错误日志都要由你的应用负责。 不要把原始异常、API Key 或其他用户的会话内容发回浏览器。
练习 9 · 给 SSE 事件做“最小必要暴露”

挑出浏览器真正需要的事件：文字增量、工具开始/结束、最终状态。不要把整个内部事件对象无脑 JSON.stringify 后发给任何客户端。

踩坑实验 · 客户端断了，Agent 还在烧钱

在 SSE 骨架里“忘掉”断连处理：浏览器发起请求后直接关掉标签页，而服务端的 session.prompt() 继续跑。

你会在 trace 里看到：模型请求没有停，文字增量继续产生，token 照常计费，直到这轮自然结束。

为什么：HTTP 连接断开不会通知 Pi——响应对象的 close 事件没人听，就什么都不会发生。

修法：监听响应的 close，断连时 await session.abort() 并取消订阅；再用 agent_settled 事件里的 aborted: true 验证真的停了。

src/data-agent.ts · 装配核心（依赖 querySalesTool 文件）
import {
  createAgentSession,
  DefaultResourceLoader,
  getAgentDir,
  ModelRuntime,
  SessionManager,
  type ExtensionFactory,
} from "@earendil-works/pi-coding-agent";
import { querySalesTool } from "./tools/query-sales.ts";

const limitGuard: ExtensionFactory = (pi) => {
  pi.on("tool_call", (event) => {
    if (event.toolName !== "query_sales") return;
    const maxRows = event.input.maxRows;
    if (typeof maxRows === "number" && maxRows > 20) {
      return {
        block: true,
        reason: "单次最多查询 20 条，请缩小范围后重试。",
      };
    }
  });
};

const loader = new DefaultResourceLoader({
  cwd: process.cwd(),
  agentDir: getAgentDir(),
  extensionFactories: [limitGuard],
  systemPromptOverride: () => [
    "你是一个销售数据分析助手。",
    "回答数字前必须先使用 query_sales 查询。",
    "不能编造数据；查询没有结果就明确说明。",
    "先给结论，再给查询依据。",
  ].join("\n"),
  appendSystemPromptOverride: () => [],
});
await loader.reload();

const modelRuntime = await ModelRuntime.create();
// 兑现第 04 课：生产代码不靠“第一个可用”碰运气。优先精确指定，
// 环境变量可覆盖（EVAL_PROVIDER / EVAL_MODEL 的习惯从评测一节延续到这里）。
const provider = process.env.AGENT_PROVIDER;
const modelId = process.env.AGENT_MODEL;
const model =
  (provider && modelId ? modelRuntime.getModel(provider, modelId) : undefined)
  ?? (await modelRuntime.getAvailable())[0];
if (!model) throw new Error("请先配置一个可用模型（或用 AGENT_PROVIDER / AGENT_MODEL 精确指定）");

const { session } = await createAgentSession({
  model,
  modelRuntime,
  resourceLoader: loader,
  customTools: [querySalesTool],
  tools: ["query_sales"],
  sessionManager: SessionManager.inMemory(),
});

const unsubscribe = session.subscribe((event) => {
  if (event.type === "tool_execution_start") {
    console.log(`\n正在调用：${event.toolName}`);
  }
  if (
    event.type === "message_update" &&
    event.assistantMessageEvent.type === "text_delta"
  ) {
    process.stdout.write(event.assistantMessageEvent.delta);
  }
});

try {
  await session.prompt("华东有哪些销售记录？请总结销售额。");
  process.stdout.write("\n");
} finally {
  unsubscribe();
  session.dispose();
}
工具限制tools: ["query_sales"] 表示只选择该工具；这个例子故意不把 bash、write、edit 等 Coding Agent 工具暴露给业务模型。
毕业标准： 你能不用复制粘贴，自己解释 ModelRuntime、ResourceLoader、AgentSession、Tool 和 Extension 各自负责什么； 能安全地加一个只读工具；知道如何从事件里观察运行；知道多用户上线还缺哪些隔离和权限工作。

现象先查哪里为什么
没有可用模型Provider、API Key、模型配置、环境变量还没走到 Agent Loop，先确认模型运行时拿到了凭据。
类型提示报错复制的代码是否与 SDK 版本相同；工具 schema 和 params 名是否一致类型检查器在帮助找出字段错配，不是模型服务报错。
模型不调用工具工具是否注册、是否激活、description 是否清晰、模型是否支持工具调用模型是基于描述选择工具；工具不在可用列表时不会调用。
钩子没有拦截是否写在 extensionFactories；事件名、返回结构和 loader.reload()扩展钩子和 subscribe 是不同通道。
Web 用户互相看到内容共享 session / 缓存的用户上下文 / 服务端授权这是应用隔离 bug，不能靠 prompt 修补。
SDK 里 mcp__* 工具不出现是否调用了 await session.bindExtensions({})；mcp.json 是否被读取MCP 连接挂在 session_start 上，不 bind 就不连（SDK 深入篇 02）。症状：不报错，但工具一直不在。
