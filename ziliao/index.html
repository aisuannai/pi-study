第 02 课 · 第一个 Agent

先让它回答一句话

最小闭环需要四样东西：可用模型、会话、一次提问，以及一个把生成文字显示出来的事件监听器。

src/hello.ts · 可直接作为第一个实验
import {
  createAgentSession,
  ModelRuntime,
} from "@earendil-works/pi-coding-agent";

// 1. 读本机模型与认证配置
const modelRuntime = await ModelRuntime.create();
const choices = await modelRuntime.getAvailable();
const model = choices[0];

if (!model) {
  throw new Error("没有可用模型：请先配置 Provider 和 API Key");
}

// 2. 创建一段对话
const { session } = await createAgentSession({
  model,
  modelRuntime,
});

// 3. 订阅文字增量
const unsubscribe = session.subscribe((event) => {
  if (
    event.type === "message_update" &&
    event.assistantMessageEvent.type === "text_delta"
  ) {
    process.stdout.write(event.assistantMessageEvent.delta);
  }
});

try {
  await session.prompt("用三句话介绍你自己。");
  process.stdout.write("\n");
} finally {
  unsubscribe();
  session.dispose();
}
读这段代码modelRuntime 管模型；session 管这一段对话；subscribe 负责“看过程”；prompt 负责“开始做”。

逐段翻译：程序是怎么走下去的

把最小示例翻译成不带术语的话
代码人话
await ModelRuntime.create()读配置，准备和模型沟通的运行时。
await modelRuntime.getAvailable()询问当前有哪些模型可以用；await 表示等结果回来再继续。
if (!model)如果列表里没有选出模型，就先报错停止；不要带着空模型继续。
createAgentSession(...)用选中的模型创建一段新的 Agent 对话。
session.subscribe(...)登记一个监听函数；Pi 发来事件时运行它。
event.type === "message_update"只处理“消息正在变化”这一类事件。检查后，TypeScript 才允许安全读取相应字段，这叫类型收窄。
await session.prompt(...)把问题交给 Agent，并等待这次处理完成。
unsubscribe(); session.dispose()停止收事件，再结束这段会话运行时。

把几个容易混淆的角色分开

ModelRuntime

像模型通讯录和钥匙管理员：知道有哪些模型、要用什么认证。

AgentSession

像一个正在进行的对话桌面：保存消息、当前模型、工具和会话状态。

prompt()

给这个对话桌面一项任务，然后等待这轮处理完成。

subscribe()

旁边的观察窗：收到文字、工具开始/结束等事件。

为什么有 finally？ 就算模型请求失败或你中途取消，清理监听器、释放 session 仍会执行。dispose() 不是“保存按钮”，会话历史的保存由 SessionManager 负责。
Node 与 TypeScript 是两件事： node src/hello.ts 负责运行；tsc --noEmit 负责检查类型。Node 不会因为你写了 : string 就替你检查变量类型。
练习 2 · 做两个小改动
  1. 把问题改成你自己感兴趣的内容。
  2. 先临时注释掉 message_update 判断，看看事件里除了文字之外还出现了什么。
  3. 再取消订阅并清理 session 的代码，想想连续运行很多次可能留下什么。

检查点：你能指出哪一行发问、哪一行输出增量、哪两行负责清理吗？

第 03 课 · 看懂 Agent 的引擎

Agent 不是一次 API 请求，而是一圈“想—做—看”

如果模型只回答文字，一轮就结束；如果它决定使用工具，Pi 会运行工具，把结果放回对话，再问模型下一步。

把词汇放进这张图里

  • Run：一次用户任务的完整处理。可能包含重试或多个 turn。
  • Turn：一次模型请求和这次回复里的工具调用处理。
  • Message：对话中的一条消息，比如 user、assistant 或 tool result。
  • Event：Pi 对外发出的“刚才发生了什么”的通知或扩展钩子。
  • Transcript：会话里的消息与结构化记录；不是单纯的屏幕输出。

源码放大镜：高层入口和循环分别在哪

按符号找源码，比记某一版的行号更可靠
你看到的行为可以去看读源码时关注
创建 SDK sessionpackages/coding-agent/src/core/sdk.ts · createAgentSession()默认组件怎么准备，如何把 runtime、工具、资源装进 session。
对话和事件packages/coding-agent/src/core/agent-session.tsprompt()、subscribe()、dispose() 的职责边界。

源码放大镜：subscribe 为什么是“观察窗”

在 Pi 1.6.1 的 AgentSession._emit() 里，事件广播的核心可以缩小成下面几行：

源码摘录 · agent-session.js · AgentSession._emit(event)
_emit(event) {
  for (const l of this._eventListeners) {
    l(event);
  }
}
白话解释Pi 把事件交给每个 listener；它不收集 listener 的返回值来决定是否执行工具。这里的调用是同步发生的，所以 listener 里做大量同步计算会拖慢派发；数据库等慢工作应放进受控队列，不要阻塞事件回调。

对应源码位置：packages/coding-agent/src/core/agent-session.ts，搜索 _emit。这就是为什么宿主层的订阅器适合显示文字、工具状态和轻量日志，而“拦截工具”要使用扩展层的决策钩子。

源码阅读技巧： 先在类型定义里找事件结构，再在发出事件的地方找调用点，最后回到 SDK 入口看是谁把它们连起来。不要从一个几千行文件第一行开始硬读。

run 结束，不一定代表真的闲下来了

Pi 可能在一次 run 后继续重试、压缩上下文，或处理排队消息。用 agent_end 判断最终空闲会过早； 若需要真正的结束通知，看 agent_settled。在 HTTP handler 里，通常等待 await session.prompt(...) 也能确定这次调用已返回。

  3. Key 是否有效、服务地址是否能访问；不要先猜代码 API 写错。

第 05 课 · 系统提示词

把通用 Agent 变成你需要的角色

提示词告诉模型“做事时遵循什么规则”。固定的人设可以在会话资源加载时设置；动态、每次请求不同的信息需要更仔细地安排注入位置。

用 ResourceLoader 设置静态人设
import {
  DefaultResourceLoader,
  getAgentDir,
} from "@earendil-works/pi-coding-agent";

const resourceLoader = new DefaultResourceLoader({
  cwd: process.cwd(),
  agentDir: getAgentDir(),
  systemPromptOverride: () => [
    "你是一个企业数据分析助手。",
    "只根据查询工具返回的数据给出数字。",
    "没有查到的数据要明确说不知道。",
    "先给结论，再给简短依据。",
  ].join("\n"),
  appendSystemPromptOverride: () => [],
});

await resourceLoader.reload();
它做了什么systemPromptOverride 提供基础提示词；reload() 让 loader 完成资源加载；再把这个 loader 交给 createAgentSession。

提示词来源的心智模型

提示词不是权限控制。 比如“用户只能看销售部数据”，不仅要写在提示词里，还要在工具执行时从认证上下文确认 userId 和部门，并对查询条件做服务端限制。
练习 5 · 写一个你自己的角色卡

用四句话写：你是谁、能做什么、不能做什么、答案应该是什么格式。替换示例中的四条规则，再问一个与你的兴趣/工作有关的问题。

检查点：让 Agent 明确说出“我不知道”的条件；不要只写“请准确回答”。

第 06 课 · 给 Agent 装一只手

工具是模型提议、你的程序执行

模型不能凭空访问你的数据库。你把可用动作定义成工具，模型选择工具并填写参数，Pi 校验参数后调用你的 TypeScript 函数。

6.1 定义一个安全的只读查询工具

src/tools/query-sales.ts · 教学用内存数据
import { Type } from "typebox";
import { defineTool } from "@earendil-works/pi-coding-agent";

const sales = [
  { region: "华东", product: "键盘", amount: 1200 },
  { region: "华南", product: "鼠标", amount: 800 },
  { region: "华东", product: "显示器", amount: 3200 },
];

export const querySalesTool = defineTool({
  name: "query_sales",
  label: "查询销售记录",
  description: "按地区查询示例销售记录。只读，不会修改数据。",
  parameters: Type.Object({
    region: Type.String({
      description: "地区名称，例如：华东",
    }),
    maxRows: Type.Optional(
      Type.Number({
        description: "最多返回几条，至少为 1",
        minimum: 1,
      }),
    ),
  }),
  async execute(_toolCallId, params, signal) {
    if (signal?.aborted) {
      return {
        content: [{ type: "text", text: "查询已取消。" }],
        details: { count: 0 },
        isError: true,
      };
    }

    const maxRows = Math.min(params.maxRows ?? 10, 20);
    const rows = sales
      .filter((row) => row.region === params.region)
      .slice(0, maxRows);

    if (rows.length === 0) {
      return {
        content: [{ type: "text", text: `没有找到 ${params.region} 的记录。` }],
        details: { count: 0 },
      };
    }

    return {
      content: [{
        type: "text",
        text: JSON.stringify(rows, null, 2),
      }],
      details: { count: rows.length },
    };
  },
});

name 和 description

名字是程序标识；描述要让模型明白何时用、做什么、不做什么。

parameters

TypeBox 描述输入形状。Pi 验证工具参数，再把类型推导传给 params。

execute

这里才是真正的业务代码。数据库权限检查、数据范围限制也必须在这里落实。

content 和 details

content 给模型看；details 可留给 UI、日志或程序处理。

当前版本的重要更新： Pi 1.6.1 的工具结果支持 isError: true。失败可以抛异常，也可以返回错误结果；普通“没有匹配数据”通常不是程序错误，应返回正常结果，不要把它标成失败。
TypeBox 的边界： Pi 用 JSON Schema 兼容的校验器处理工具参数。基础的 Type.String、Type.Number、Type.Object 适合教学；不要假设 TypeBox 所有运行时扩展特性都一定会执行。
练习 6 · 给工具加一个筛选条件
  1. 为 schema 增加可选的 product 字符串参数。
  2. 在 filter 里同时检查地区和产品。
  3. 把结果条数限制在合理范围。

检查点：即使模型传入很大的 maxRows，你的 execute 也必须有服务端上限。

第 07 课 · 扩展与事件

观察事件，和改变 Agent 行为，是两种不同工作

这一章是整个 SDK 最关键的机制之一。记住一个小口诀：subscribe 多用于观察； pi.on 用于扩展钩子，可以按事件契约影响流程。

两种事件接口的职责
对比session.subscribe()pi.on()
在哪里写宿主代码：CLI、服务端 handler 等扩展工厂函数里
适合做什么输出 token、展示工具进度、状态日志拦截工具、改写输入、调整请求上下文
能不能影响流程不要依赖 listener 的返回值；它是观察通道有些事件会等待 handler，并读取指定格式的返回值
慢 I/O 的影响listener 返回类型是同步回调；长任务也要注意队列与错误处理决策/转换 handler 可能阻塞主流程，避免在里面等待慢网络操作

7.1 1.6.1 的工具事件时序

真实源码也按这个顺序组织。注意：Agent 核心层的默认 toolExecution 是 "parallel"，同一轮里有多个工具调用时，各工具的事件会交错出现；只有配置为 "sequential"，或工具自己声明 executionMode: "sequential" 时，才走下面这条顺序路径。下面是 Pi 1.6.1 中顺序工具执行路径的缩小摘录（省略错误处理和并行执行分支）：

源码摘录 · agent-loop.js · executeToolCallsSequential()
await emit({
  type: "tool_execution_start",
  toolCallId: toolCall.id,
  toolName: toolCall.name,
  args: toolCall.arguments,
});
const preparation = await prepareToolCall(
  currentContext, assistantMessage, toolCall, config, signal,
);

let finalized;
if (preparation.kind === "immediate") {
  finalized = {
    toolCall,
    result: preparation.result,
    isError: preparation.isError,
  };
} else {
  const executed = await executePreparedToolCall(
    preparation, signal, emitToolExecutionUpdate(toolCall, emit),
  );
  finalized = await finalizeExecutedToolCall(
    currentContext, assistantMessage, preparation, executed, config, signal,
  );
}

await emitToolExecutionEnd(finalized, emit);
const toolResultMessage = createToolResultMessage(finalized);
await emitToolResultMessage(toolResultMessage, emit);
读懂关键点tool_execution_start 在 prepareToolCall 前；扩展的 tool_call 安检发生在准备阶段；如果结果是 immediate（例如被拦截），就不会进入 executePreparedToolCall。

7.2 写一道工具调用的安全门

扩展里的 tool_call 钩子
import type { ExtensionFactory } from "@earendil-works/pi-coding-agent";

const limitGuard: ExtensionFactory = (pi) => {
  pi.on("tool_call", (event) => {
    if (event.toolName !== "query_sales") return;

    const maxRows = event.input.maxRows;
    if (typeof maxRows === "number" && maxRows > 20) {
      return {
        block: true,
        reason: "单次最多查询 20 条，请缩小范围后重试。",
      };
    }
  });
};

事件 tool_call 的参数类型里可能装着任意 JSON 值，所以示例先用 typeof 检查，不假设模型一定遵守类型。真正的硬上限仍建议在工具 execute 内再次检查。

7.3 每个事件有自己的契约

tool_call

工具执行前检查；可以返回 block: true 拦截。要改参数时，原地修改 event.input，而不是返回新参数。

context

每次模型请求前处理对话消息；这个事件里的 messages 不包含系统提示词。

context_with_system

需要查看或转换完整上下文（含 system message）时使用；返回消息列表意味着你拥有它的内容。

tool_result

执行之后观察或改写返回给模型的结果；不要与“工具开始执行”混为一谈。

审计时序别踩坑： 被 block 的工具也会有 tool_execution_start 和带错误结果的 tool_execution_end；它不代表业务 execute() 真的跑过。 需要统计实际执行次数时，记录 tool_call 是否被拦截，或在工具内部打审计记录。
练习 7 · 设计“观察”和“干预”两种逻辑
  1. 用 session.subscribe 显示“正在查询销售数据”。
  2. 用 pi.on("tool_call") 拦截超过上限的查询。
  3. 说清楚：为什么不能指望 subscribe 回调的 return 值阻止工具运行？

提示：一种是旁观通知，一种是 SDK 定义的扩展钩子；后者的特定事件会读取约定返回值。

第 08 课 · 会话、记忆与隔离

“记住聊天”不等于“所有用户共用一份状态”

一个 session 是一段对话。多轮聊天需要复用同一个用户的会话；不同用户要有不同会话和授权上下文。

SessionManager.inMemory()

适合实验或由应用自己保存对话；进程重启后，内存中的历史会消失。

默认会话管理

适合本地单用户体验，但 Web 多用户通常要把用户 ID、会话 ID 与存储记录关联起来。

AgentSessionRuntime

进阶的会话生命周期工具，支持替换/恢复/分叉等操作；入门先理解 session，再学它。

服务端设计原则： 每个请求先认证用户，再按 userId 找到其 session；工具每次执行都确认用户可以访问该数据。 不能只把 userId 拼进提示词就认为权限隔离完成了。
练习 8 · 找出这个设计的 bug

服务端只有一个全局变量 let session，所有用户登录后都共用它。会发生什么？

答案方向：历史可能串线、并发 prompt 冲突、用户上下文或授权信息可能混用。至少要按已认证用户隔离 session 和用户上下文。

import {
  createAgentSession,
  DefaultResourceLoader,
  getAgentDir,
  ModelRuntime,
  SessionManager,
  type ExtensionFactory,
} from "@earendil-works/pi-coding-agent";
import { querySalesTool } from "./tools/query-sales.ts";

const limitGuard: ExtensionFactory = (pi) => {
  pi.on("tool_call", (event) => {
    if (event.toolName !== "query_sales") return;
    const maxRows = event.input.maxRows;
    if (typeof maxRows === "number" && maxRows > 20) {
      return {
        block: true,
        reason: "单次最多查询 20 条，请缩小范围后重试。",
      };
    }
  });
};

const loader = new DefaultResourceLoader({
  cwd: process.cwd(),
  agentDir: getAgentDir(),
  extensionFactories: [limitGuard],
  systemPromptOverride: () => [
    "你是一个销售数据分析助手。",
    "回答数字前必须先使用 query_sales 查询。",
    "不能编造数据；查询没有结果就明确说明。",
    "先给结论，再给查询依据。",
  ].join("\n"),
  appendSystemPromptOverride: () => [],
});
await loader.reload();

const modelRuntime = await ModelRuntime.create();
const model = (await modelRuntime.getAvailable())[0];
if (!model) throw new Error("请先配置一个可用模型");

const { session } = await createAgentSession({
  model,
  modelRuntime,
  resourceLoader: loader,
  customTools: [querySalesTool],
  tools: ["query_sales"],
  sessionManager: SessionManager.inMemory(),
});

const unsubscribe = session.subscribe((event) => {
  if (event.type === "tool_execution_start") {
    console.log(`\n正在调用：${event.toolName}`);
  }
  if (
    event.type === "message_update" &&
    event.assistantMessageEvent.type === "text_delta"
  ) {
    process.stdout.write(event.assistantMessageEvent.delta);
  }
});

try {
  await session.prompt("华东有哪些销售记录？请总结销售额。");
  process.stdout.write("\n");
} finally {
  unsubscribe();
  session.dispose();
}

B.1 扩展放在哪里

B.2 一个完整的最小扩展

~/.pi/agent/extensions/my-extension.ts
import { type ExtensionAPI, isToolCallEventType } from "@earendil-works/pi-coding-agent";
import { Type } from "typebox";

export default function (pi: ExtensionAPI) {
  // 1. 订阅事件
  pi.on("session_start", async (_event, ctx) => {
    ctx.ui.notify("扩展已加载！", "info");
  });

  pi.on("tool_call", async (event, ctx) => {
    if (isToolCallEventType("bash", event) && event.input.command.includes("rm -rf")) {
      const ok = await ctx.ui.confirm("危险操作", "允许执行 rm -rf 吗？");
      if (!ok) return { block: true, reason: "用户拒绝" };
    }
  });

  // 2. 注册一个给模型用的工具
  pi.registerTool({
    name: "greet",
    label: "打招呼",
    description: "按名字向某人打招呼",
    parameters: Type.Object({
      name: Type.String({ description: "要打招呼的人" }),
    }),
    async execute(toolCallId, params, signal, onUpdate, ctx) {
      return {
        content: [{ type: "text", text: `你好，${params.name}！` }],
        details: {},
      };
    },
  });

  // 3. 注册一个给用户用的斜杠命令
  pi.registerCommand("hello", {
    description: "打个招呼",
    handler: async (args, ctx) => {
      ctx.ui.notify(`你好 ${args || "世界"}！`, "info");
    },
  });
}

这段代码展示了扩展最常用的三件事：订阅事件（pi.on）、注册能力（registerTool、registerCommand），以及通过 ctx.ui 与用户交互。

B.3 ExtensionAPI 的主要入口

扩展工厂函数拿到的 pi 对象能做什么
方法用途
pi.on(event, handler)订阅事件；返回的函数可以取消这一个订阅。
pi.registerTool(definition)注册模型能调用的工具（第 6 课的内容）。
pi.registerCommand(name, options)注册用户输入的斜杠命令。
pi.registerShortcut(key, options)注册键盘快捷键。
pi.registerFlag(name, options)注册 CLI 参数。
pi.registerProvider(name, config)动态注册或覆盖模型供应商（第 4 课的进阶版）。
pi.sendUserMessage() / pi.sendMessage()由扩展主动发消息给会话。
pi.exec(command, args)不经过 shell 直接执行命令。
注册工具可以在运行中进行： registerTool() 不只在加载时调用，也可以在 session_start 或命令处理函数里调用，新工具会立即出现，不需要 /reload。

B.4 一次 prompt 的完整事件顺序

这是整个扩展机制的核心。下面的顺序来自官方文档的生命周期说明：

一次用户输入从头到尾经过的事件
用户输入
 ├─ 扩展命令 /name        命中则直接执行，后面的 input 不再触发
 ├─ input                 可以 continue / transform / handled
 ├─ 展开 /skill:xxx 与 /template
 ├─ before_agent_start    可以注入消息、修改本轮系统提示词
 ├─ agent_start
 │   └─ turn_start                    （每一轮：一次模型请求 + 工具调用）
 │       ├─ context → context_with_system
 │       ├─ before_provider_headers → before_provider_request
 │       ├─ after_provider_response → provider_stream_event
 │       ├─ message_start / message_update / message_end
 │       └─ 每个工具调用：
 │            tool_execution_start
 │            tool_call            可以 block，或原地修改 input
 │            tool_execution_update
 │            tool_result         可以修改结果
 │            tool_execution_end
 │   └─ turn_end
 ├─ agent_end              ⚠ 不代表真正空闲：可能还会重试或处理排队消息
 ├─ agent_before_settle    最后一个可以追加条目、请求继续的点
 └─ agent_settled          最终状态，只通知，适合更新界面状态
别把 agent_end 当成“完成”： 它之后 Pi 仍可能自动重试、压缩上下文，或者处理排队的消息。需要“真正空闲”的通知，用 agent_settled。

B.5 事件的四种处理模式

同一个事件的处理方式取决于它属于哪一类。读文档时先确认这一点：

事件的几种模式
模式含义例子
通知返回值被忽略，只用来观察。agent_settled、thinking_level_select、provider_stream_event
原地修改直接修改传进来的对象。tool_call 的 event.input、before_provider_headers 的 headers
链式转换后面的处理器拿到前面返回的结果。context、tool_result（可返回部分字段）
门控返回特定结果就终止这次操作。input 返回 handled、tool_call 返回 block、session_before_compact 取消

这正是第 7 课的口诀在完整版里的样子：订阅（subscribe）只用来观察；扩展事件才能按契约影响流程。

B.6 tool_call：拦截与改参数

扩展里改写 bash 命令参数并拦截危险命令
import { isToolCallEventType } from "@earendil-works/pi-coding-agent";

pi.on("tool_call", async (event, ctx) => {
  if (isToolCallEventType("bash", event)) {
    // 原地修改参数：改动会真正作用到工具执行上
    event.input.command = `source ~/.profile\n${event.input.command}`;

    if (event.input.command.includes("rm -rf")) {
      return { block: true, reason: "危险命令", terminate: true };
    }
  }
});
修改参数之后不会重新校验。 如果你把 maxRows 改成了不合法的值，工具会直接收到它。所以关键限制仍然要在工具的 execute 里再检查一次（第 7 课已经强调过）。

B.7 input：在模型看到之前改写用户输入

把 “?quick …” 转换成简短回答的请求
pi.on("input", async (event, ctx) => {
  if (event.text.startsWith("?quick ")) {
    return { action: "transform", text: `请简短回答：${event.text.slice(7)}` };
  }
  if (event.text === "ping") {
    ctx.ui.notify("pong", "info");
    return { action: "handled" };       // 不调用模型
  }
  return { action: "continue" };        // 默认：原样放行
});

input 看到的是用户输入的原始文本，斜杠模板和技能还没有展开。返回值有三种：continue 放行，transform 改写后继续，handled 直接结束、不进入模型。

B.8 会话与资源相关的事件

常用的会话、资源事件
事件什么时候
session_start会话启动、加载、重载或切换后。event.reason 说明原因。
session_shutdown会话即将结束。用来关闭在 session_start 中打开的资源。
session_before_compact压缩前，可以取消或自定义压缩。
session_before_switch执行 /new 或 /resume 之前。
model_select用户切换模型时。恢复会话时不会触发，需在 session_start 里读取 ctx.model。
resources_discover会话启动后，扩展可以再添加技能、模板、主题的路径。
不要在扩展工厂函数里启动后台资源。 进程、socket、文件监听、定时器都应该延迟到 session_start 或真正需要它的时候启动，并在 session_shutdown 里关闭。因为工厂函数可能在根本没有会话的情况下运行。

B.9 写扩展的几条规则

  1. 先判断事件类型。只想观察，就用通知型事件；要干预，就用门控或转换型事件。
  2. 流式事件（如 message_update）里不要做慢操作。通知回调应保持轻量，慢的工作放进队列。
  3. 安全相关的门控要“失败即拒绝”。如果安全判断做不出来，就返回 block，而不是默认放行。
  4. 把 ctx.signal 传给你发起的请求。这样用户按 Escape 时，你的 fetch 也会被取消。
  5. 用 CONFIG_DIR_NAME 构造配置路径，不要硬编码 .pi。这样在改名的发行版里也能正常工作。

进阶篇 C · 会话与上下文

会话是一棵树，上下文是它的一条分支

第 8 课讲了“每个用户一个 session”。这里讲另一面：一个会话里可以有多条分支，模型每次只看见当前这一条，而历史太长时，Pi 会把旧内容压缩成摘要。

C.1 续接与切换

不同入口决定会话在哪个工作目录里运行
入口工作目录
pi --continue当前目录
pi --resume、/resume、--session会话自己记录的目录，可能和当前目录不同
pi --fork当前目录，并生成一个新会话

每个会话都记录创建时的工作目录，而且之后不会改变。工具、@路径、项目配置都从这个目录解析。如果目录已经不存在（例如项目被改名），交互模式会问你：在当前目录继续、分叉成新会话，或取消。

用 /name 给会话起名字，用 /session 查看当前会话文件、ID、消息数、Token 用量和费用。

C.2 分支：/tree、/fork、/clone

Pi 把会话存成树。回到较早的位置并不会删除你离开的那条路，只是换了一条分支继续。

三种分支操作的区别
操作结果适合
/tree在同一个会话文件里移动相关的几种尝试想放在一起
/fork从较早的一条用户消息开新会话这条路应该变成独立的工作
/clone把当前分支复制成新会话想保留当前状态的一份副本

在 /tree 里选中一条用户消息，它的文字会回到编辑框，修改后提交就会形成一条新分支。离开一条分支时，Pi 可以把那条分支总结成一段摘要，附在你进入的分支上，保留有用的结论，却不带上全部消息。

C.3 上下文压缩（compaction）

自动压缩的触发条件可以用一行公式概括：

自动压缩的触发条件（来自官方压缩文档）
contextTokens > contextWindow - reserveTokens

默认 reserveTokens 是 16384。压缩的过程是：

  1. 从最新的消息往回数，累计到约 keepRecentTokens（默认 20000）为止，这里就是切分点；
  2. 切分点之前的消息交给模型生成结构化摘要，如果之前已经压缩过，会把旧摘要一起带上；
  3. 在会话里追加一条 compaction 条目，记录摘要和保留的起点；
  4. 之后发给模型的是：系统提示词 + 摘要 + 切分点之后的消息。
压缩不删除原始记录。 被摘要的消息仍然保存在会话文件里，只是不再发送给模型。导出或回溯时都还能看到。

切分点有规则：不会切在工具结果上，因为工具结果必须和它的工具调用放在一起。

C.4 手动压缩与设置

在 Pi 里手动压缩，可附加压缩重点
/compact
/compact 只保留数据库迁移相关的决定和未解决的问题
~/.pi/agent/settings.json · 压缩相关设置
{
  "compaction": {
    "enabled": true,
    "reserveTokens": 16384,
    "keepRecentTokens": 20000
  }
}

关掉自动压缩（enabled: false）不会影响手动的 /compact。压缩失败时（例如服务暂时不可用），修好服务后再执行一次 /compact 即可。

C.5 扩展可以接管压缩

压缩前后都有事件：session_before_compact 可以取消压缩，或者自己提供摘要；压缩完成后是 session_compact，失败则是 session_compact_failed。这给了你在团队场景里定制摘要格式的机会，比如固定保留“已确定的决策”这一栏。

摘要是有损的。 模型可能遗漏细节。重要的约束（比如“不要改 API 返回格式”）最好同时写进 AGENTS.md，它每次都会加载，不会因为压缩而消失。
练习 C · 制造一次分支，再压缩一次

  2. 用 /session 查看消息数，再执行 /compact，再看一次消息数和上下文用量。

进阶篇 D · 集成与对外接口

让别的程序用 Pi：JSON、RPC 与 MCP

第 9 课我们自己用 SSE 把 Agent 推给浏览器。Pi 其实已经提供了几种现成的对外接口，你要先选对方式，再动手。

D.1 先选接口

几种集成方式的区别（来自官方 RPC 文档）
方式进程边界控制方式适合
SDK同一进程直接调用 TypeScript 方法和事件Node.js / Bun 宿主，需要完整 API
RPC子进程stdin/stdout 上的 JSONL 命令、响应和事件其他语言、IDE、自定义界面

Node.js 或 Bun 宿主，优先用 SDK。 子进程形式只在你需要进程隔离、或者宿主不是 JavaScript 时才值得。

D.2 JSON 模式：一次运行的事件流

终端：输出 JSONL 事件并保存
pi --mode json "Review this repository" > events.jsonl

输出的第一行是会话头，之后每行是一个事件。一次简单运行大致是这样的：

events.jsonl（节选，每行一个对象）
{"type":"session","version":3,"id":"uuid","timestamp":"2024-12-03T14:00:00.000Z","cwd":"/path"}
{"type":"agent_start"}
{"type":"turn_start"}
{"type":"message_update","assistantMessageEvent":{"type":"text_delta","contentIndex":0,"delta":"Hello"}}
{"type":"turn_end","message":{"role":"assistant"},"toolResults":[]}
{"type":"agent_end","messages":[],"willRetry":false}
{"type":"agent_settled","aborted":false}
解析 JSONL 不要用 readline。 Node 的 readline 还会把 U+2028、U+2029 当作换行，而它们在 JSON 字符串里是合法的。应该按字节或 UTF-8 流读取，只用 LF 切分。另外 stdout 只放协议数据，日志写到 stderr；读取 stdout 要持续进行，否则管道堵住会让 Pi 停下。

注意 agent_end 与 agent_settled 的区别（进阶 B 已经讲过）：前者只结束一轮低级运行，后者才表示 Pi 不会再自动继续。

D.3 RPC 模式：长期运行的子进程

终端：启动 RPC 子进程（不落盘）
pi --mode rpc --no-session

之后通过 stdin 发送 JSON 命令，每条命令可以带一个字符串 id，响应会带回同一个 id。命令处理是异步的，所以要按 ID 对应，而不是按顺序对应：

stdin 发送 / stdout 返回
{"id":"req-2","type":"prompt","message":"Review this repository"}
{"id":"req-2","type":"response","command":"prompt","success":true,"data":{"disposition":"started"}}
“prompt 成功”不代表模型已经回答完。 响应只说明这条消息被接受、排队或处理了。需要知道什么时候真正结束，要持续读取事件，并等待 agent_settled。如果响应的 disposition 是 "handled"，就根本没有开始新的运行，不要再等它。

如果你用 TypeScript 作为宿主，不必自己拼协议，可以使用导出的 RpcClient，它负责启动子进程、按 ID 配对响应，并把事件交给监听器：

src/rpc-demo.ts · 用 RpcClient 控制子进程
import { RpcClient } from "@earendil-works/pi-coding-agent";

const client = new RpcClient({ cwd: process.cwd() });
await client.start();
try {
  const events = await client.promptAndWait("华东有哪些销售记录？");
  console.log(`收到 ${events.length} 个事件`);
} finally {
  await client.stop();
}

D.4 MCP：把外部服务变成工具

MCP（Model Context Protocol）让 Pi 接入别人写好的工具服务器，不用你自己在扩展里重写。它支持本地 stdio 和远程 HTTP 两种方式。

终端：添加服务器、检查连接、启动 Pi
pi mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem .
pi mcp add docs --url https://example.com/mcp --bearer-token-env-var DOCS_TOKEN
pi mcp list
pi

服务器配置保存在 ~/.pi/agent/mcp.json（个人使用）或 .pi/mcp.json（项目共用，需要信任项目后才加载）：

~/.pi/agent/mcp.json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "."]
    },
    "docs": {
      "url": "https://example.com/mcp",
      "headers": { "Authorization": "Bearer ${DOCS_TOKEN}" },
      "description": "Search and read the product documentation"
    }
  }
}
  • 工具名会变成 mcp__<服务器名>__<工具名>，一眼就能看出来源。
  • command 只能是一个可执行文件，参数放在 args 里，不是一整条 shell 命令。
  • 凭据用 ${ENV} 引用环境变量，不要直接写进文件。
  • 远程服务支持 OAuth：只写 url，遇到需要登录时用 /mcp login 服务器名。
  • 在会话里用 /mcp 查看状态、重连、启用或禁用某个服务器；修改配置文件后执行 /reload。
MCP 服务器就是可执行代码。 它的工具拥有和 Pi 相同的权限。只添加你信任的服务器，项目级的 .pi/mcp.json 尤其要先审查。

D.5 和第 9 课的 SSE 方案怎么选

自己写 SSE 服务与使用 RPC 的取舍
问题自己写 SSE 服务（第 9 课）RPC 子进程
鉴权、用户隔离你自己负责，通常更灵活要自己在外层做，Pi 只是子进程
进程隔离与 Web 服务同进程Pi 在独立进程里，崩溃不拖垮宿主
会话多路复用你决定一个用户对应哪个 session每个子进程通常对应一个会话，需要自己管理进程池
开发量要自己拼事件、断线取消协议已定义好，但要管理子进程生命周期

无论哪种方式，多用户场景下的隔离和授权都是你的责任。Pi 的协议不替你做这些。

进阶篇 F · 安全与上线

把 Agent 放进边界里运行

Pi 默认以你的系统用户身份运行，能读写你能访问的所有文件，并且不会为每次工具调用请求确认。这一节讲清楚边界在哪里，以及怎样把它收紧。

F.1 威胁来自哪里

  • 提示注入：文件内容、网页、命令输出、项目指令都可能夹带诱导模型执行危险操作的文字。
  • 模型的错误判断：它可能删错文件、运行错误的命令，或者把数据发到不该去的地方。
  • 扩展、技能、MCP 服务器：它们作为 Pi 的一部分运行，权限与 Pi 相同。
查看对话记录、使用项目信任，都不是安全边界。 它们只能帮你发现问题，不能阻止问题发生。真正的边界来自操作系统、容器或虚拟机。

F.2 项目信任

当一个目录含有 .pi/settings.json、.pi/mcp.json、.pi/extensions、.pi/skills、.pi/prompts 等项目资源时，Pi 会先询问是否信任。信任之后，这些项目资源才会加载，包括项目扩展和项目里的 MCP 服务器。

信任决定的来源，按优先级排列
顺序来源
1命令行的 --approve / --no-approve
2用户级或命令行扩展的 project_trust 事件
3保存过的决定（/trust 写入 ~/.pi/agent/trust.json）
4全局设置 defaultProjectTrust，默认 "ask"

在打印、JSON、RPC 模式下没有交互提示。如果自动化脚本需要加载项目资源，要显式加上 --approve。

F.3 选择隔离方式

几种常见的隔离方式（节选）
方式Pi 运行的位置适合
直接运行你的系统用户只能靠专用账号收窄权限，共享系统和网络
普通 Docker 容器容器内，包括内置工具和扩展最直接的本地边界，适合大多数人
托管沙箱（如 Docker Sandboxes、OpenShell）受管理的沙箱需要更细的网络和凭据策略
扩展方式（如 Gondolin）宿主机，只隔离内置工具只想隔离命令执行，其他扩展仍在宿主机上

隔离的范围取决于你暴露了什么。把整个 ~/.pi/agent 挂进容器，等于把凭据和会话都交出去了；读写挂载的工作目录，改动也会直接写回宿主机。

F.4 一个最小的 Docker 运行方式

Dockerfile.pi
FROM node:24-bookworm-slim

RUN apt-get update \
  && apt-get install -y --no-install-recommends bash ca-certificates git ripgrep \
  && rm -rf /var/lib/apt/lists/*
RUN npm install -g --ignore-scripts @earendil-works/pi-coding-agent

WORKDIR /workspace
ENTRYPOINT ["pi"]
终端：只挂载当前工作目录，配置放在命名卷里
docker build -t pi-sandbox -f Dockerfile.pi .
docker run --rm -it \
  -e ANTHROPIC_API_KEY \
  -v "$PWD:/workspace" \
  -v pi-agent-home:/root/.pi/agent \
  pi-sandbox

这里 -v pi-agent-home:/root/.pi/agent 用的是独立的命名卷，而不是宿主机的 ~/.pi/agent。进入 Pi 后执行 !pwd，应该看到 /workspace，说明挂载正确。

F.5 上线前的检查清单

  1. Pi 只能访问任务需要的文件和服务。
  2. 凭据用环境变量或短期令牌，不写进仓库、截图或分享的会话。
  3. 网络访问按需开放，任务不需要联网就关掉。
  4. 扩展、技能、MCP 服务器都审查过来源和代码。
  5. 重要改动前有备份或版本控制，结果在应用到其他系统前先看 diff。
  6. 导出或分享会话前先检查，里面可能包含文件内容、命令输出和曾经暴露的凭据。
练习 F · 画出你的边界

对你计划运行 Pi 的任务，回答下面三个问题：

  1. Pi 需要读写哪些目录？哪些绝对不能让它碰到？
  2. 它需要哪些凭据？能否换成只读或短期的？
  3. 它需要联网吗？如果不需要，你打算怎样关掉网络？

检查点：按这三点写出的挂载或权限方案，能否在不依赖“提示词写得好”的前提下成立？
