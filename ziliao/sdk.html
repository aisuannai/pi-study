SDK 深入篇 01 · 先分清边界

SDK 会话默认加载什么，不加载什么

SDK 不是“缩水版 CLI”，CLI 也不是另一个产品——两者跑的是同一个引擎。区别在于：CLI 替你把所有线接好了， SDK 把接线权交给你。这张对照表决定你“少配了什么”时去哪找答案。

CLI 启动与 SDK createAgentSession() 的默认行为对照
资源CLI（pi 命令）SDK（createAgentSession）
扩展文件发现自动（~/.pi/agent/extensions、.pi/extensions）相同（DefaultResourceLoader.reload()）
内置扩展（codemode / tool_search / MCP）自动加载不加载，要手动加进 extensionFactories
MCP 服务器连接启动即连加 createMcpExtension() 后，还要调 session.bindExtensions()
技能（skills）自动发现相同（~/.pi/agent/skills、.pi/skills）
提示词模板 / 主题 / 上下文文件自动发现相同
设置（settings.json）自动读取相同；可用 SettingsManager.applyOverrides() 覆盖
会话持久化默认落盘默认落盘；SessionManager.inMemory() 关闭
系统提示词组装SYSTEM.md / APPEND_SYSTEM.md / AGENTS.md / 技能完全相同
最容易踩的坑： “CLI 里能用，SDK 里不见了”的三大件——codemode、tool_search、MCP——都是 CLI 的内置扩展。 SDK 会话不会加载它们，需要你显式安装（见本篇 04 节）。
练习 01 · 盘点你的会话加载了什么

在任意一个教程示例里，loader.reload() 之后加两行：

console.log(loader.getExtensions().extensions.length, "个扩展")
console.log(loader.getSkills().skills.map((s) => s.name))

检查点：对照表格，说得出每一项“是 SDK 默认给的，还是你自己接的线”。

SDK 深入篇 02 · 扩展

扩展在 SDK 里的三种接法与生效时机

能。CLI 里的扩展机制在 SDK 里原样可用，而且多了一种“进程内内联”的接法。三种接法可以混用： 文件自动发现、显式路径、内联工厂。

2.1 三种接法

扩展接入 SDK 的三种方式
接法写法适合
① 内联工厂extensionFactories: [(pi) => { ... }]宿主自己的逻辑；随应用分发，不落文件
② 文件自动发现放到 ~/.pi/agent/extensions/ 或 .pi/extensions/（信任后）本地通用增强；与 CLI 共享
③ 显式路径additionalExtensionPaths: ["./my-ext.ts"]随仓库走的专用扩展；jiti 直接加载 TS，无需编译
三种接法并存（官方 06-extensions.ts 的模式）
const loader = new DefaultResourceLoader({
  cwd: process.cwd(),
  agentDir: getAgentDir(),
  additionalExtensionPaths: ["./my-logging-extension.ts"],   // ③ 显式路径
  extensionFactories: [
    (pi) => {                                                  // ① 内联工厂
      pi.on("agent_start", () => console.log("[inline] 运行开始"));
    },
  ],
});
await loader.reload();   // ② 此时自动发现 ~/.pi/agent/extensions 等位置

要把扩展分发给团队或公网，走 settings.json 的 packages 字段 （npm / git 来源，pi install 安装）——见 cli.html 进阶篇 B 的扩展位置表。

2.2 生效时机：钩子立即生效，session_start 要等 bind

这是源码里确认过、文档里一句带过的重要细节：

扩展能力在 SDK 里的生效时机
能力何时生效
pi.on("tool_call") 等运行期钩子createAgentSession() 返回后立即生效——ExtensionRunner 在会话构造函数里就创建了
registerTool() 注册的工具同一时机，进入可调用集合
session_start / resources_discover 事件要等宿主调用 await session.bindExtensions({})
MCP 服务器连接bindExtensions() 触发 session_start 后，后台连接
ctx.ui 交互（confirm / select）通过 bindExtensions({ uiContext }) 注入——SDK 宿主自己决定界面长什么样
session_shutdown 清理通过 bindExtensions({ shutdownHandler }) 挂载宿主自己的清理逻辑
教程主线的验证： 毕业实战的 limitGuard 用 tool_call 钩子，没调 bindExtensions 也生效—— 因为运行期钩子在会话构造时就挂好了。但如果扩展依赖 session_start 初始化资源 （进阶篇 B.8 的规则），SDK 宿主就必须补一句 await session.bindExtensions({})。
练习 02 · 验证生效时机
  1. 写一个内联扩展：session_start 打一条日志，tool_call 打另一条。
  2. 不调 bindExtensions 直接 prompt：只有 tool_call 的日志出现。
  3. 补上 await session.bindExtensions({}) 再跑：两条都出现。

检查点：说得出为什么 MCP 必须要 bindExtensions，而安全门不用。

SDK 深入篇 03 · 技能

Skill 在 SDK 里：发现、过滤与注入

进阶篇 A.7 讲的是“用”技能，这一节讲“SDK 宿主怎么管理”技能。发现机制与 CLI 完全相同； 你多拿到的是过滤、内联和诊断能力。

3.1 发现：和 CLI 同一条路径

DefaultResourceLoader.reload() 会从 cwd/.pi/skills、~/.pi/agent/skills 以及 settings 的 skills 路径发现技能（解析 SKILL.md frontmatter），随系统提示词把 名字 + 描述交给模型，任务匹配时模型才读取全文——A.7 的渐进加载在 SDK 里一字不差地生效。

查看当前会话发现了哪些技能（官方 04-skills.ts 模式）
const loader = new DefaultResourceLoader({
  cwd: process.cwd(),
  agentDir: getAgentDir(),
});
await loader.reload();

const { skills, diagnostics } = loader.getSkills();
console.log("发现的技能：", skills.map((s) => s.name));
if (diagnostics.length > 0) console.log("警告：", diagnostics);

3.2 过滤与内联：skillsOverride

宿主可以用 skillsOverride 对技能做最终裁决——过滤、改名，或塞入完全内联、不落磁盘的技能：

skillsOverride：过滤 + 内联技能
import { createSyntheticSourceInfo, type Skill } from "@earendil-works/pi-coding-agent";

const customSkill: Skill = {
  name: "data-agent-rules",
  description: "DataAgent 的回答规则。回答销售数据问题时使用。",
  filePath: "/virtual/SKILL.md",
  baseDir: "/virtual",
  sourceInfo: createSyntheticSourceInfo("/virtual/SKILL.md", { source: "sdk" }),
  disableModelInvocation: false,
};

const loader = new DefaultResourceLoader({
  cwd: process.cwd(),
  agentDir: getAgentDir(),
  skillsOverride: (current) => ({
    // 只保留匹配的技能，再附上内联技能
    skills: [
      ...current.skills.filter((s) => s.name.startsWith("data-")),
      customSkill,
    ],
    diagnostics: current.diagnostics,
  }),
});
什么时候用技能，什么时候用 systemPromptOverride？ 每次都必须生效的规则进系统提示词（第 05 课）；只在特定任务类型时才需要的大段说明做成技能。 它们共享同一个上下文预算——技能是“按需加载”的那一半（高级篇 G.2 的上下文税）。
练习 03 · 给 DataAgent 挂一个技能
  1. 在 ~/.pi/agent/skills/sales-faq/SKILL.md 写一个销售 FAQ 技能，description 写清“什么时候用”。
  2. 用 loader.getSkills() 确认它被发现。
  3. 问一个 FAQ 覆盖的问题，观察模型是否读取了技能全文。

检查点：把 description 改得含糊（“帮助处理销售”），路由效果变差了吗？

SDK 深入篇 04 · MCP

MCP 在 SDK 里：三个工厂 + 一次 bind

进阶篇 D.4 是 CLI 视角（pi mcp add 命令）。SDK 视角下，MCP 是一个官方提供的扩展工厂： 把它加进 extensionFactories，配置仍来自同一份 mcp.json，最后在会话上 bind 一次。

src/mcp-session.ts · SDK 接入 MCP（官方 14 号示例的模式）
import {
  createAgentSession,
  createCodemodeExtension,
  createMcpExtension,
  createToolSearchExtension,
  DefaultResourceLoader,
  getAgentDir,
  ModelRuntime,
  SessionManager,
  SettingsManager,
} from "@earendil-works/pi-coding-agent";

const cwd = process.cwd();

const resourceLoader = new DefaultResourceLoader({
  cwd,
  agentDir: getAgentDir(),
  extensionFactories: [
    createCodemodeExtension({ mode: "on" }),   // 可选：codemode 工具
    createToolSearchExtension(),               // 可选：tool_search 工具
    createMcpExtension(),                      // 读取 agent 目录与受信任项目的 mcp.json，与 CLI 相同
  ],
});
await resourceLoader.reload();

// codemode / tool_search 注册时是“未激活”状态，用 defaultTools 打开
const settingsManager = SettingsManager.create(cwd);
settingsManager.applyOverrides({ defaultTools: ["+codemode", "+tool_search"] });

const modelRuntime = await ModelRuntime.create();
const model = (await modelRuntime.getAvailable())[0];
if (!model) throw new Error("没有可用模型：请先配置 Provider 和 API Key");

const { session } = await createAgentSession({
  model,
  modelRuntime,
  resourceLoader,
  settingsManager,
  sessionManager: SessionManager.inMemory(),
});

try {
  // 发出 session_start：MCP 服务器在后台开始连接
  await session.bindExtensions({});
  console.log("活动工具：", session.getActiveToolNames().join(", "));

  session.subscribe((event) => {
    if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
      process.stdout.write(event.assistantMessageEvent.delta);
    }
  });
  await session.prompt("用文件系统工具列出当前目录里的 Markdown 文件。");
  console.log();
} finally {
  session.dispose();
}
  • 工具命名不变：MCP 工具叫 mcp__<服务器>__<工具>，在 getActiveToolNames() 里一眼可辨。
  • exposure 概念不变：deferred 暴露的 MCP 工具靠 tool_search 按需加载，codemode 暴露的进 codemode 脚本——SDK 与 CLI 行为一致。
  • 项目级 mcp.json：同样要求项目受信任后才读取（进阶篇 F.2）。
忘了 bind 的典型症状： 不报错，但 mcp__* 工具一直不出现，而 CLI 里 pi mcp list 一切正常。 回到本篇 02 节的生效时机表——MCP 连接挂在 session_start 上。
练习 04 · 把文件系统 MCP 接进 DataAgent
  1. 先用 CLI 加配置：pi mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem .
  2. 按本节代码在 SDK 会话里接上 MCP，bindExtensions() 前后各打印一次 getActiveToolNames()。
  3. 问“当前目录里有什么文件”，观察模型调用 mcp__filesystem__* 工具。

检查点：去掉 +codemode 后，deferred 的 MCP 工具还能被直接声明吗？（提示：exposure。）

SDK 深入篇 05 · 运行机制总纲

Pi 的完整生命周期：进程 → 扩展运行时 → 会话 → run

你猜的方向是对的——Pi 确实有一套贯穿始终的生命周期。它此前分散在进阶篇 B.4（扩展事件）、进阶篇 C（会话树）、 高级篇 J（run 内部），这一节把它们串成一张总图，并标出每一层里 CLI 与 SDK 的分野。

5.1 四层结构，各管一段

进程、扩展运行时、会话、run 的职责与生命周期事件
层活多久关键事件 / APICLI vs SDK
进程整次运行settings、凭据、模型目录加载CLI 自动；SDK 在 createAgentSession 前后由你控制
扩展运行时随会话创建，reload 时重建工厂函数 → 钩子注册；bindExtensions()CLI 自动 bind；SDK 要显式调用才有 session_start
会话session_start → session_shutdownsession_start（reason: startup/new/resume/fork/reload）、resources_discover、session_shutdownCLI 由 /new、/resume 驱动；SDK 用 AgentSessionRuntime 切换
run一次用户任务input → before_agent_start → agent_start → turn* → agent_end → before_settle → settled两边完全一致（高级篇 J 逐行走过的就是这一层）

5.2 会话替换：shutdown 不是进程退出

/new、/resume、/reload 走同一条路： session_shutdown（带 reason）→ 扩展清理资源 → 重建扩展运行时 → 新的 session_start。 所以进阶篇 B.8 的规则在 SDK 里同样成立：后台资源在 session_start 启动、在 session_shutdown 关闭；SDK 宿主可以在 bindExtensions({ shutdownHandler }) 里挂自己的清理逻辑。

5.3 把整张图变成你的架构

进程层

凭据注入（高级篇 I.3）、日志、限流——这是你的 Web 服务（实战篇）。

扩展运行时层

能力边界：工具、命令、门控、审计——大多在工厂函数里完成。

会话层

隔离与记忆：每用户一份（第 08、09 课与实战篇），树与压缩在进阶篇 C。

run 层

单次任务的质量与成本：提示词、工具设计、thinking level、观测（高级篇 H）。

练习 05 · 画出你自己的介入点

拿你的 DataAgent 项目回答：进程层你写了什么？扩展层注册了哪些钩子？会话层怎么隔离？run 层观测什么？

检查点：任何一个“Pi 行为不符合预期”的问题，你都应该能先定位到这四层中的一层，再去找对应的事件或源码。

学 Pi Agent 的目标不是背 API，而是知道每一层负责什么、出问题该去哪一层找。
